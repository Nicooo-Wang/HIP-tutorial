§1硬件心智模型

写快 kernel 之前，需要一张“脑内地图”：计算在哪里发生，数据放在哪里，各处有多大、多快。Lab 0 §2 已经画过 MI308X 的整体结构，这里只补充本课要用的部分。§1.3 把所有数字汇总成一张表，后面各节和 Assignment 的书面问题都会回来查它。

§1.1计算层级：XCD → CU → SIMD → wavefront

一张 MI308X 有 4 个 XCD，每个 XCD 有 20 个 CU，共 80 个 CU。每个 CU 有 4 个 SIMD。你写的 block 会被整个放到某一个 CU 上，再切成若干个 64 线程的 wavefront，分给这个 CU 的 4 个 SIMD 执行。

一个 SIMD 上同时“驻留”着好几个 wavefront，这是 Lab 0 没细说的一点。本机每个 CU 最多驻留 32 个 wavefront，也就是每个 SIMD 最多 8 个。SIMD 每个周期从驻留的 wavefront 里挑一个“已经准备好”的，发射它的下一条指令。某个 wavefront 在等显存数据时（要几百到上千个周期），SIMD 就去执行别的 wavefront。

GPU 主要靠这种切换来掩盖访存延迟，这叫延迟掩盖。所以同时驻留的 wavefront 要足够多，这是性能的前提，§2.4 会再谈。

§1.2内存层级：寄存器 / LDS / L2 / Infinity Cache / HBM

kernel 能用到的存储从近到远是：

  • 寄存器（VGPR，向量通用寄存器）：每个线程私有，最快。线程用到的局部标量通常放在寄存器里，例如累加器 acc。局部变量实际放在哪里由编译器决定：局部数组、或寄存器不够时“溢出”的值，可能被放进 scratch（每个线程私有的一块显存，慢得多）。§5.4 讲怎样检查。
  • LDS（Local Data Share）：每个 CU 一块 64 KiB 的片上存储，同一个 block 的线程共享，延迟远低于显存。代码里用 __shared__ 声明（§3.4）。CUDA 资料里叫 shared memory。
  • L1 / L2 缓存：硬件自动管理。每个 CU 有 32 KiB L1，每个 XCD 有 4 MiB L2。缓存以 128 字节的 cache line 为单位管理数据（rocminfo 的 Cacheline Size: 128）。这个数字是 §3.1 合并访存的基础。
  • Infinity Cache：256 MiB，全卡共享，位于 L2 和 HBM 之间。数据放得进它、又被反复读取时，由它直接供给，有效带宽可以高于 HBM 本身。
  • HBM 显存（global memory）：约 192 GiB，hipMalloc 分配的内存都在这里。所有 CU 都能访问，容量最大，但最慢。

HBM 峰值带宽怎么来的。带宽 = 总位宽 × 每引脚数据率（每根数据线每秒传输的比特数）。本机 HBM3 的总位宽是 8192 bit（8 个 HBM 堆栈 × 1024 bit）。每引脚数据率取 AMD 规格给出的 5.2 Gb/s。这个数正好是显存时钟 1.3 GHz 的 4 倍，但它是查规格得到的，不是由时钟推出来的：

8192 bit × (1.3 GHz × 4) ÷ 8 bit/B = 5324.8 GB/s ≈ 5.3 TB/s

这和 amd-smi static 直接报告的 MAX_BANDWIDTH: 5325 GB/s 一致，也与 AMD 官方给出的 MI300X（同为 8 个 HBM3 堆栈、5.2 Gb/s）的 5.3 TB/s 相同。

fp32 向量峰值怎么来的。峰值 = CU 数 × 每 CU 每周期浮点运算数 × 频率。AMD 的 CDNA3 白皮书和 MI300X 数据表给出 MI300X 的 fp32 向量峰值：163.4 TFLOPS = 304 CU × 2.1 GHz × 256 FLOP/周期/CU。每 CU 每周期 256 FLOP 是这样来的：4 个 SIMD × 每 SIMD 每周期 32 个 fp32 FMA × 每个 FMA 2 FLOP。FMA（fused multiply-add）是一条算 a × b + c 的指令，一次乘、一次加，计 2 次浮点运算（FLOP）。代入本机的 80 个 CU 和最高频率 1.85 GHz：

80 CU × 256 FLOP/周期/CU × 1.85 GHz = 37.9 TFLOPS

实测 FMA 吞吐约 28 TFLOPS，比理论值 37.9 TFLOPS 低约四分之一。主要原因是频率：本机跑 kernel 时核心频率实测约 1.39–1.42 GHz，达不到最高的 1.85 GHz。按 1.39 GHz 算，80 × 256 × 1.39 GHz ≈ 28 TFLOPS，正好对上。

另外，要接近峰值，指令和操作数也要合适，细节在下面的折叠框里。和理论峰值比较时，要把频率和指令这两个因素考虑进去。

满速 FMA 对指令和操作数有什么要求

每 SIMD 每周期 32 个 FMA 有两条路可达：

  • 编译器生成 packed 指令 v_pk_fma_f32，一条指令同时做两个 fp32 FMA；
  • 普通的 v_fma_f32 由同一 SIMD 上的两个 wavefront 在同一周期双发射。这要求每个 SIMD 至少驻留 2 个 wavefront，并且操作数不能来自标量寄存器（SGPR）。SGPR 是一个 wavefront 所有 lane 共用的寄存器，例如直接拿 kernel 参数 alpha 当乘数时，它就在 SGPR 里。

本机微基准：操作数全在向量寄存器里的 v_fma_f32 约 26.5 TFLOPS，v_pk_fma_f32 约 28.3 TFLOPS；读 SGPR 操作数的 v_fma_f32 只有约 14 TFLOPS。每个 SIMD 只驻留 1 个 wavefront 时，也只有约一半速率。§5 的 GEMM 内层乘加的操作数来自 LDS 和寄存器，不用 packed 指令也能接近全速。

频率用 rocm-smi --showclocks 查看。它与负载大小基本无关：只占 8 个 CU 时也是约 1.42 GHz。

理论的 5.3 TB/s 在实践中摸不到。本机实测，显存到显存拷贝（hipMemcpy D2D，读 + 写，由 ROCm 运行时自己的 kernel 完成）约 2.0–2.2 TB/s；一个简单的只读 kernel 约 3–3.6 TB/s，随数据量和时刻波动。两者都远低于理论值。

所以 Lab 1 的访存类性能用例（a2、a3）以拷贝带宽为“尺子”：先在同一进程里测一次 D2D 拷贝带宽，再要求你的 kernel 达到它的某个比例。本课程把“你的带宽 ÷ 同进程实测拷贝带宽”叫作比值。Lab 1 的阈值和参考数字写成百分比（14% 就是比值 0.14），Lab 2 起判分输出和 README 直接写比值。机器被别人占用时两者一起变慢，比值仍然公平。

这只是一种归一化，拷贝带宽不是上限：以读为主的 kernel（例如 a3 的归约）完全可以超过它。

§1.4两块天花板：带宽与算力

有了这两个峰值，就能估计一个 kernel 最快能多快。设 kernel 每从显存搬 1 字节做 I 次浮点运算。I 叫计算强度，单位 FLOP/B。在只考虑 HBM 带宽和 fp32 算力的简单模型里，kernel 的速度不会超过：

min( 算力峰值 , 带宽峰值 × I )

两个上限在 I = 37.9 TFLOPS ÷ 5.3 TB/s ≈ 7 FLOP/B 处相交。I 低于约 7 时带宽上限更低，这类 kernel 叫访存密集，优化重点是数据搬运。I 高于约 7 时算力上限更低，叫计算密集。这个模型能告诉你该往哪个方向优化，但 kernel 实际卡在哪里，还要测量确认。

kernel 为什么可能远低于这两条上限

这个模型只看两种资源，实际的 kernel 常常两条上限都没碰到。常见原因有：

  • 驻留的 wavefront 太少，延迟掩盖不住（§2.4）；
  • 屏障等待、地址计算等额外指令占了时间（§3.5、§5.3）；
  • LDS 访问有 bank conflict，或 LDS 带宽成了瓶颈（§3.6）；
  • 数据量很小时，kernel 启动本身的开销就占了大头。

另外，图里的带宽用的是理论峰值。实测能达到的带宽更低（§1.3），所以访存密集 kernel 的实际天花板也更低。

本课前三个问题（向量加法、转置、归约）都是访存密集的，优化目标是不浪费每一字节的搬运。第四个问题 GEMM 展示怎样通过数据复用，把 kernel 从访存密集推向计算密集。

§2从 vector add 开始

向量加法 c[i] = a[i] + b[i] 是最简单的并行问题：元素之间互不相关。它在 Lab 0 里已经以“填下标”的形式出现过。这一节借它把 kernel 的执行模型讲完整，并引入一个以后天天用的写法：grid-stride loop。

§2.1SIMT 与 wavefront

你写 kernel 时，写的是一个线程的程序；硬件执行时，是一个 wavefront 的 64 个线程一起执行同一条指令。wavefront 里的每个线程也叫一个 lane，编号 0–63。每个 lane 用自己的寄存器，所以有自己的 threadIdx.x、自己的 i。这种模型叫 SIMT（Single Instruction, Multiple Threads）。

那 if 怎么办？64 个 lane 共用一条指令流，不能一半走 then、一半走 else。硬件用一个 64 位的执行掩码（EXEC mask）解决：条件为假的 lane 被暂时“关掉”，指令照样发出，但被关掉的 lane 不写结果。如果两条分支都有 lane 要走，wavefront 先在掩码下执行 then，再翻转掩码执行 else，两段的时间都要花。这叫分支发散（divergence）。

由此得到两条直觉：① 同一个 wavefront 内的 lane 最好走同一条路径；② 只有 wavefront 内部路径不一致（分支发散）时，才要付出两条路径都执行一遍的额外代价。整个 wavefront 走同一条路径时，分支只剩条件判断和跳转本身的少量开销。这两条在 §4.2 讲归约时会用到。

§2.2kernel 与 launch

启动语法在 Lab 0 §3.1 讲过：kernel<<<grid, block, 动态 LDS 字节数, stream>>>(参数…)。本课的 LDS 都用 __shared__ 静态声明（§3.4），第 3 个参数一律填 0。下面补充五点本课要用的细节：

  • 参数按值传进 kernel。指针参数传的是地址值；float alpha 这样的标量直接拷进 kernel，每个线程都能读。指针必须指向 GPU 能访问的内存，通常就是显存。Assignment 里的指针都已经是 hipMalloc 分配的。
  • grid 和 block 可以是二维、三维。写成 dim3 block(64, 4)，kernel 里用 threadIdx.y、blockIdx.y、blockDim.y、gridDim.y 取 y 方向的值。§3.2 的转置会用到。一维时直接写整数，等价于 dim3(n, 1, 1)。
  • gridDim：gridDim.x 是 grid 在 x 方向的 block 数，与 blockDim 对称。§2.5 要用它。
  • 启动是异步的（Lab 0 §4.2）。Assignment 的启动函数会收到一个 stream 参数，原样传给启动语句即可。测试负责同步和检查错误。
  • __device__ 函数与模板 kernel。__global__ 函数是从主机启动的 kernel，返回类型必须是 void。__device__ 修饰的是只能在 GPU 上调用的普通函数，调用者是 kernel 或别的 __device__ 函数，可以有返回值，例如 __device__ float wave_reduce(float v)。kernel 也可以是模板，启动时把模板参数写在名字后面：partial_sum_kernel<true><<<grid, block, 0, stream>>>(…)。编译器为每个用到的模板参数各生成一份 kernel。a3 的骨架两种写法都用到了。
启动语句的第 3 个参数到底是什么

它是动态 LDS 的字节数，只给 extern __shared__ 声明的数组用，大小在启动时才决定。它会叠加在 kernel 里静态 __shared__ 数组的用量之上。

所以不要把静态数组的大小再填进第 3 个参数：那样每个 block 会多占一倍 LDS，一个 CU 能驻留的 block 变少；总量超过 64 KiB 时启动直接失败。

§2.3全局下标与边界检查

这一步 Lab 0 a1 已经做过，这里只复习要点。一维 grid 中每个线程的全局下标是“前面所有 block 的线程数 + 本 block 内的编号”：

i = blockIdx.x × blockDim.x + threadIdx.x

启动的线程总数通常比 n 多，因为最后一个 block 不满。所以访问 a[i]、b[i]、c[i] 之前必须判断 i < n，否则多出来的线程会读写数组之外的内存。

Lab 1 的测试用哨兵区检测越界写（原理见 Lab 0 §1.3），并在调用你的代码前把输出填成 NaN。失败信息里“得到 nan”，通常说明那个元素没有任何线程写过。另一种可能是越界读：哨兵区里填的也是 NaN，越界读进来的值一旦参与运算，结果就是 NaN。

vector add 的测试要求 GPU 结果和 CPU 上 float 加法的结果数值完全相等，容差为 0。两个有限的 float 相加，CPU 和 GPU 都按 IEEE 754 舍入到最近，结果是唯一确定的。只要你老老实实写一次 float 加法（不先转 double、不加别的运算），就一定相等。

“零容差比较”和“逐位相同”有什么区别

测试比较的是数值：|GPU − CPU| ≤ 0。所以 +0 和 −0 算相等，虽然它们的二进制位不同。测试输入是 [−1, 1) 里的随机数，不会出现 NaN 和无穷大。

“结果唯一确定”还有一个前提：默认的编译选项。像 -ffast-math 这样的选项允许编译器改写浮点运算，本课不用。

§2.4选 block 大小

grid 的大小由 n 和 block 大小决定：向上取整，即 Lab 0 §3.3 的 (n + B - 1) / B。block 大小 B 是你自己选的。选法有三条规则，从硬到软：

  1. 不超过 1024（§1.3 表）。超过时启动直接失败（hipErrorInvalidConfiguration）。
  2. 取 64 的倍数。硬件按 64 个线程一组切 wavefront。block = 100 时，第二个 wavefront 只有 36 个 lane 有活干，其余 28 个 lane 的算力白白浪费。
  3. 让每个 CU 能驻留足够多的 wavefront（occupancy，占用率）。

第 3 条展开说。§1.1 讲过，SIMD 靠在多个驻留的 wavefront 之间切换来掩盖访存延迟。每个 CU 最多驻留 32 个 wavefront（2048 个线程）。实际能驻留多少，取决于下面三种资源中最先用完的那个：

  • wavefront 槽位：每个 CU 32 个。block = 1024（16 个 wavefront）时，一个 CU 最多放 2 个 block。
  • 寄存器：每个线程用的寄存器越多，能同时驻留的 wavefront 越少。rocprofv3 的 trace 里，VGPR_Count 列是每个线程分配到的向量寄存器数（Lab 0 §6.3）。它按分配粒度向上取整，比实际用到的略多。编译时也能直接看到，见 §5.4。
  • LDS：一个 block 用 48 KiB LDS 时，64 KiB 的 CU 里只放得下 1 个这样的 block（§3.4 再谈）。

驻留的 wavefront 数 ÷ 32 就是占用率（occupancy）。占用率不是越高越好：每个线程多用一些寄存器，往往能多干一些活。但对向量加法这种纯访存 kernel，驻留的 wavefront 够不够多，直接决定能不能把显存带宽吃满。

实践中 256 是稳妥的默认值。不用 LDS、寄存器也用得少的 kernel，只要 grid 里的 block 足够多，实测 64、128、256、1024 这四种 block 大小都能让每个 CU 驻满 32 个 wavefront（见下面的折叠框）。其他大小还要算一算完整的 block 能不能正好填满 32 个槽位：例如 768 线程的 block 有 12 个 wavefront，一个 CU 只放得下 2 个，共 24 个 wavefront。block 太大的问题在另一头：n 不大时 block 数少，可能只占用少数几个 CU。256 线程（4 个 wavefront）在两头都不吃亏。

§2.5grid-stride loop

到目前为止都是“线程数 ≥ n，每个线程处理一个元素”。如果 grid 的大小是固定的，而 n 远大于线程总数呢？固定 grid 的原因可能是想让 block 数正好是 CU 数的整数倍，也可能像 a3 那样受工作区大小限制。

答案是让每个线程循环。把整个 grid 看成一把宽度为 T = gridDim.x × blockDim.x 的“扫帚”：第一次扫过元素 [0, T)，然后整体向前挪 T，扫 [T, 2T)，依此类推，直到越过 n。每个线程从自己的全局下标出发，每次前进 T。这叫 grid-stride loop（按网格跨度循环）。下面用另一个问题演示写法：fill 把数组全部填成某个值，相当于 float 版的 memset。

// p[0..n) 全部置为 v；grid 可以是任意大小
__global__ void fill_kernel(float* p, float v, int n) {
  const int stride = gridDim.x * blockDim.x;          // grid 的线程总数 T
  for (int i = blockIdx.x * blockDim.x + threadIdx.x; // 起点：全局下标
       i < n;                                          // 兼做边界检查
       i += stride) {                                  // 整个 grid 前进 T
    p[i] = v;
  }
}

void launch_fill(float* p, float v, int n, hipStream_t stream) {
  fill_kernel<<<160, 256, 0, stream>>>(p, v, n);   // 160 个 block，与 n 无关
}

注意三件事：

  • 循环条件 i < n 本身就是边界检查。n 小于线程总数时，很多线程一次都不进循环；n 很大时，每个线程转 ⌈n/T⌉ 或 ⌊n/T⌋ 圈。
  • 每一圈里，同一个 wavefront 的 64 个 lane 仍然访问 64 个相邻元素。这一点对显存效率至关重要（§3.1）。反过来让每个线程处理“自己连续的一段”（线程 0 处理 0–99，线程 1 处理 100–199……），同一时刻 64 个 lane 的地址就相隔 100 个元素，访存效率会大跌。在下面的小部件里切换两种映射，对比每一步访问的元素分布。
  • grid 大小与正确性解耦了。grid 设成 1 也能算对，只是慢；设成多少只影响性能。
下标用 int 会不会溢出

n 接近 231 时，i += stride 可能超出 int 的范围，而有符号整数溢出是未定义行为。本课的规模远小于此，用 int 没问题；以后处理更大的数组，下标要换成 size_t 或 int64_t。

Part B 的 launch_saxpy 把 grid 固定为 kSaxpyGrid = 160 个 block × 256 线程，共 40960 个线程。用例 saxpy_needs_stride 的 n 是它的 37 倍多。只改 kernel，不要改 grid 和启动语句。

另外，saxpy 的 y 既是输入也是输出。每个元素读一次、写一次，且只由一个线程负责，所以不会有两个线程抢同一个元素。

§3访存模式与转置

向量加法里，访存模式天然正确：相邻线程访问相邻元素。矩阵转置是第一个需要你主动设计访存模式的问题。它的读和写方向天生互相垂直，不可能同时顺着内存走，除非借助片上的 LDS 中转。

§3.1合并访存

显存访问不是按“一个 float”处理的。一个 wavefront 执行一条 load 指令时，64 个 lane 各给出一个地址；硬件把落在同一条 128 字节 cache line 里的地址合并成一次访问。所以判断访存好坏，先看这 64 个地址落在多少条 cache line 里：涉及的 line 越多，要发出的内存请求就越多。

  • 64 个 lane 访问 64 个连续的 float：共 256 字节。起始地址按 128 字节对齐时，正好落在 2 条 cache line 里，取到的数据全部有用。这叫合并访存（coalesced access）。
  • 64 个 lane 访问间隔很大的地址（比如每个 lane 相隔矩阵的一整行）：落在 64 条不同的 cache line 里，要发出 64 次 cache line 级的访问，只为了其中的 256 字节。按整条 line 计算，有用的数据只占 1/32。
“按整条 line 计算”的字节数等于实际 HBM 流量吗

不一定。图 3.1 里的“利用率 1/32”是按整条 cache line 计算的：64 条 × 128 字节 = 8192 字节里只用了 256 字节。gfx942 的 L2 向显存取数据时，可以只取一条 line 中 32 或 64 字节的一部分，所以实际的 HBM 流量可能比这个数小。

但 64 次 cache line 级访问的请求开销是实打实的，跨步访问依然慢得多。§3.3 的实测是：naive 转置的有效带宽只有拷贝带宽的约 6%。

记住这个口诀：让 threadIdx.x 相邻的线程访问相邻的地址。行主序矩阵中“相邻的地址”是同一行的相邻列，所以通常让 x 方向的线程对应列号。

§3.22D 网格与 naive 转置

矩阵天然是二维的，用二维的 block 和 grid 覆盖它最顺手。dim3 block(64, 4) 是一个 64 × 4 的线程块：256 个线程，4 个 wavefront。线程在块内的坐标是 (threadIdx.x, threadIdx.y)。

wavefront 按“x 先变”的顺序切分。线程的线性编号是 threadIdx.y × blockDim.x + threadIdx.x，所以 blockDim.x = 64 时，每个 wavefront 恰好是 threadIdx.y 相同的一整行 64 个线程。

每个维度的全局坐标和一维时一样算：x 方向是 blockIdx.x × blockDim.x + threadIdx.x，y 方向把 x 全换成 y。grid 在每个维度上分别向上取整，例如 a2 骨架里已经给出的：

dim3 block(64, 4);
dim3 grid((cols + block.x - 1) / block.x,    // x 方向覆盖所有列
          (rows + block.y - 1) / block.y);   // y 方向覆盖所有行

于是 x 方向的全局坐标是列号 c，y 方向的是行号 r。两个方向都可能有多出来的线程，所以边界检查要同时检查 r < rows 和 c < cols。

naive 转置就是“每个线程搬一个元素”：算出自己的 (r, c)，检查边界，从 in 的 (r, c) 读、往 out 的 (c, r) 写。

§3.3为什么 naive 转置的写是非合并的

用 §3.1 的标准检查一个 wavefront：它是 threadIdx.y 相同、threadIdx.x = 0…63 的 64 个线程，即同一个 r、连续的 64 个 c。

  • 读 in[r × cols + c]：c 连续 → 地址连续 → 2 条 cache line，合并。
  • 写 out[c × rows + r]：c 每加 1，地址加 rows 个元素。rows = 8192 时相邻 lane 相隔 32 KiB，64 个地址落在 64 条 cache line 里，每条只写 4 字节。

反过来让 x 对应 r 也没用：写变连续了，读却变成跨步。转置的读和写方向天生垂直，只要每个线程“读一个、写同一个”，总有一边是跨步的。本机实测（8192 × 8192，空闲 MI308X），naive 转置的有效带宽（§3.7 定义）只有 D2D 拷贝带宽的约 6%。

缓存能部分挽救跨步写：相邻几个 wavefront（不同的 r）写的是同一批 cache line 里相邻的 4 字节。如果这些 line 还留在 L2 里，这些写就能合并。但矩阵一大，L2 装不下这么多“只写了一点”的 line，挽救就失效了。6% 就是结果。

§3.4LDS 是什么、__shared__ 与生命周期

解决办法是加一个“中转站”：先把一小块矩阵按行从 in 合并地读进片上存储，再从片上存储按列取出来，按行合并地写进 out。片上存储里的“按列取”不涉及 cache line，代价很小，但它有自己的规则（§3.6）。这块片上存储就是 LDS。

LDS 的要点：

  • 声明：在 kernel（或 __device__ 函数）里写 __shared__ float tile[R][C];。尺寸必须是编译期常量（字面量或 constexpr）。
  • 作用域与可见性：每个 block 有自己独立的一份；同一个 block 的所有线程看到的是同一份，不同 block 之间互不可见。
  • 生命周期：block 开始时分配，block 结束时消失。LDS 不会被初始化：内容不确定，可能是之前别的 block 留下的值。要先写入再读。
  • 容量：每个 block 最多 64 KiB（§1.3）。像这样静态声明（尺寸写在代码里）时，超过就会编译报错。例如 __shared__ float s[16385];（65540 字节）在本机报 error: local memory (65540) exceeds limit (65536)。报错里的 local memory 指的就是 LDS，不是线程私有的局部变量。每个 CU 也只有 64 KiB LDS，所以一个 block 用的 LDS 越多，一个 CU 上能同时驻留的 block 越少（§2.4）。

下面是 LDS 的一个最小例子（不是转置）：每个 block 把自己负责的 256 个元素倒序写回。线程 t 在第 ③ 步读的，是线程 255 − t 在第 ① 步写的槽位。可见 LDS 让线程能读到别的线程的数据：

constexpr int kB = 256;
// 假设 n 是 kB 的整数倍：每个 block 把 in 中自己那 256 个元素倒序写到 out
__global__ void reverse_each_block(const float* in, float* out) {
  __shared__ float buf[kB];                              // 每个 block 一份，block 结束即消失
  const int base = blockIdx.x * kB;
  buf[threadIdx.x] = in[base + threadIdx.x];             // ① 合并地读入 LDS
  __syncthreads();                                       // ② 等全 block 都写完（§3.5）
  out[base + threadIdx.x] = buf[kB - 1 - threadIdx.x];   // ③ 读别的线程写的槽位，合并地写出
}

tile 与 block 的形状

分块转置要先定两个形状：tile 是一个 block 负责的子矩阵（例如 64 × 64），block 是线程的排布。两者不必相同：

  • 让 block 的 x 维 = tile 宽度 = 64。这样一个 wavefront 正好读入 tile 的一整行：64 个连续 float，合并。
  • 64 × 64 = 4096 个元素，超过了 block 最多 1024 个线程，所以 block 的 y 维要取得更小（例如 4、8 或 16），每个线程在 y 方向循环处理多行。线程 (x, y) 负责 tile 的第 y、y + blockDim.y、y + 2·blockDim.y……行。这和 §2.5 的 grid-stride loop 是同一个思路，只是跨度换成了 blockDim.y。
  • grid 按 tile 来数：x 方向需要 ⌈cols / tile⌉ 个 block，y 方向需要 ⌈rows / tile⌉ 个。block (bx, by) 负责 in 中左上角为 (r0, c0) = (by·tile, bx·tile) 的子块。
  • 写出阶段：这个 tile 在 out 中的左上角是 (c0, r0)。仍然让 x 方向的 64 个线程对应 out 某一行里连续的 64 列，也就是 in 中连续的 64 行。这样写 out 是合并的。代价是它们从 LDS 取的是 tile 的一列，这正是 §3.6 要处理的情形。
  • 矩阵边长不一定是 tile 的整数倍，读入和写出时都要做边界检查。写出时目标是 out，它的行数、列数和 in 互换了。

§3.5__syncthreads 与“同步屏障”

一个 block 里有好几个 wavefront，它们由硬件独立调度，进度互不相同。wavefront 0 已经执行到第 ③ 步时，wavefront 3 可能还没开始第 ① 步。如果没有第 ② 步，wavefront 0 读到的 buf[kB - 1 - threadIdx.x] 可能还是没写入的旧值。

__syncthreads() 是一道屏障（barrier）。block 中的每个线程到达这里时停下等待，直到全部线程都到达，才一起继续。并且屏障之前写入 LDS 的数据，屏障之后对 block 内所有线程都可见。

block 里所有线程都必须执行到同一个 __syncthreads()。把它写进只有部分线程会进入的 if，例如边界检查 if (r < rows) { …; __syncthreads(); }，是未定义行为：可能挂起，也可能结果错误。正确做法是让边界检查只包住读写语句，屏障放在所有分支之外。

两个线程访问同一个地址、至少一个是写、中间又没有同步，这叫数据竞争（race）。它的结果取决于各 wavefront 的相对快慢，而快慢又受调度和机器负载影响。漏掉屏障的程序可能在小矩阵上、在空闲的卡上恰好通过，换个尺寸或换个时间就错。

所以“测试通过”不能证明没有竞争，要靠推理：每一次读 LDS，都要问“写它的那个线程，一定已经写完了吗？”

§3.6bank conflict 与 padding

LDS 内部被分成 32 个 bank，每个 bank 4 字节宽；地址按 4 字节一格轮流分给各 bank：

bank = (字节地址 ÷ 4) mod 32 　// 对 float 数组 s[k]，就是 k mod 32

每个 bank 每个周期只能服务一个地址。一个 wavefront 读 LDS 时（每个 lane 读 4 字节），64 个 lane 分成前后两半，每半 32 个 lane 一批，同时访问 32 个 bank。同一批里如果有 k 个 lane 访问同一个 bank 的不同地址，这个 bank 要分 k 轮服务，这叫 k 路 bank conflict。多个 lane 读同一个地址不算冲突，硬件会广播。

转置的第 ③ 步“按列取”正好撞上最坏情况。设 __shared__ float tile[64][64]，一个 wavefront 的 lane x 读 tile[x][y]（固定的 y），地址是 x × 64 + y：

bank = (x × 64 + y) mod 32 = y mod 32 　// 与 x 无关！

所有 lane 都落进同一个 bank，是 32 路冲突：按这个模型，这一步要 32 轮才能完成。修复方法简单得惊人：每行多开一列，tile[64][64 + 1]。这时地址是 x × 65 + y，bank = (x + y) mod 32，相邻 lane 落在相邻 bank，冲突消失。多出的那一列从不存数据，只用来错开每一行的起始 bank，这叫 padding。代价是 64 × 4 = 256 字节 LDS。

这个模型针对每个 lane 读写 4 字节（例如 float）的 LDS 访问。本机微基准的结果与它吻合，细节见下面的折叠框。用 float2、float4 一次读写 8 或 16 字节时，lane 的分组方式不同，后面的 Lab 用到时再讲。

本机验证：跨步读取的实测，以及“两半各一批”的证据

微基准一：每个 lane 读 s[lane × stride]（ds_read_b32，每 lane 4 字节），改变 stride 测时间。本机 GPU 7，各 stride 的访问次数相同：

耗时倍数1.01.83.57.114.128.21.028.21.0

耗时与“32 个 bank、每半个 wavefront 一批”的模型吻合。倍数略低于预测，因为循环里还有别的开销：k 路冲突表示 bank 要多服务 k − 1 轮，整条指令或整个 kernel 的耗时不一定正好变成 k 倍。stride 64 和 32 一样慢、而不是更慢，说明 bank 数是 32 而不是 64。CUDA 资料里“32 个 bank”的结论在这里也成立，但背后的 wavefront 是 64 宽，别把两件事混在一起。

微基准二直接验证“两半各一批”：让前 32 个 lane 都读 bank 0、后 32 个 lane 都读 bank 1，耗时与 64 个 lane 全读 bank 0 一样，都约为无冲突时的 12 倍。如果 64 个 lane 是一起处理的，前一种情况应该只有后一种的一半。这个微基准的循环开销比微基准一大，所以倍数整体偏低，要看的是两种情况之间的比例。

§3.7用带宽衡量 kernel、读懂 lds_bandwidth 用例

访存密集的 kernel 用有效带宽衡量：kernel 逻辑上必须读写的字节数 ÷ 耗时。转置读 rows × cols 个 float、写同样多：

有效带宽 = 2 × rows × cols × 4 字节 ÷ 耗时

“逻辑上必须”是关键：缓存未命中时多搬的字节、cache line 里没用上的字节都不算。所以 naive 转置虽然让显存忙得要死，有效带宽却很低，因为它的大部分搬运都是浪费。

lds_bandwidth 用例在 8192 × 8192 上测你的 launch_transpose_lds。它取多次运行中最快的一次算有效带宽，并逐元素校验整个输出，防止“什么都不做所以很快”。然后与同一进程里测得的 D2D 拷贝带宽比较（同样按读 + 写计算，见 §1.3），达到 14% 才通过。

空闲 MI308X 上的参考数字：naive 约 6%；参考实现约 31–35%，它是一个简单的 64 × 64 带 padding 的 LDS 分块；更好的设计可以更高，本机测到过约 55–60% 的实现。所以只要 tile、合并、同步都对了，阈值留有充足余量。如果你的 LDS 版本没过，最可能的原因是读或写仍有一边不合并。

如果 launch_transpose_lds 还在调用 naive 版本，你会看到类似这样的输出（数字是示意）：

  lds_bandwidth............................... FAIL (0/3)  [139.0 GB/s]
    带宽 139 GB/s，低于目标 304 GB/s（= 14% × 本次实测拷贝带宽 2170 GB/s）

方括号里是你的有效带宽。机器繁忙时数字会整体下降；但阈值跟着同进程的拷贝带宽走，判定基本不受影响。

§4归约

归约（reduction）把 n 个数合成一个：求和、求最大值、求范数。它是 softmax、layernorm、注意力里必不可少的一步，也是第一个需要线程合作出结果的问题：每个线程只知道自己那部分，答案却要汇总全体。

§4.1两遍归约结构

归约要分两遍做，因为一个 kernel 里，不同 block 之间没有屏障。block 内的线程可以靠 LDS 和 __syncthreads() 合作，但 __syncthreads() 只管本 block 的线程。不同 block 可能在不同 CU 上、以任意顺序执行，甚至不会同时存在：block 数超过 GPU 能同时容纳的数量时，后面的 block 要等前面的退出才开始。所以在 kernel 里，没法等“全体 block 都算完部分和”之后再汇总。

最直接、最可靠的全局屏障是 kernel 边界：同一个 stream 里，第二个 kernel 一定在第一个全部结束之后才开始。于是第 1 遍让每个 block 算出一个部分和，写进工作区 ws；第 2 遍只用 1 个 block，把这些部分和加起来（图 4.1）。

只用一个 kernel 也能完成归约，但要用到原子操作。原子操作保证多个线程对同一个地址做“读—加—写”时不会互相覆盖，§4.5 末尾会介绍其中的 atomicAdd。a3 书面问题 4 请你想一想这个方案。

HIP 里有没有能同步全体 block 的办法

有，但不是普通的 kernel 启动。HIP 提供 cooperative launch：用 hipLaunchCooperativeKernel 启动，kernel 里用 cooperative groups 的 this_grid().sync() 同步全体 block。

它的前提是所有 block 能同时驻留在 GPU 上，所以 block 数有上限，不能像普通启动那样随 n 增长。本课不用它。“全体 block 常驻、在 kernel 内协作”这类设计，研究 mega kernel 时会再遇到。

a3 的骨架已经写好了这个结构。下面四点是骨架里的设计选择，你要读懂：

  • block 数有上限。骨架里 blocks = min(⌈n / kBlock⌉, kMaxBlocks)。kBlock = 256 是每个 block 的线程数，kMaxBlocks = 1024 是 block 数的上限。每个 block 要在工作区里占一个位置写部分和，而工作区 ws 只有 4096 个 float（骨架里的常量 kWorkspaceFloats），所以上限不能超过 4096。
  • block 数要多到能填满 SIMD。§1.1 讲过，SIMD 靠在多个驻留的 wavefront 之间切换来掩盖显存延迟。每个 block 有 256 ÷ 64 = 4 个 wavefront，全卡有 80 × 4 = 320 个 SIMD。如果只用 256 个 block，一共 1024 个 wavefront，每个 SIMD 平均只分到 3.2 个，离每个 SIMD 最多驻留 8 个还差得远。全卡最多同时驻留 320 × 8 = 2560 个 wavefront，也就是 640 个 block；骨架的上限 1024 超过了 640，能把全卡填满。两种设置的实测带宽见下方提示框。
  • 每个线程先用 grid-stride loop 累加。block 数有上限，n 大时线程数不够“一线程一元素”，这正是 §2.5 的情况。每个线程先用 grid-stride loop 把自己负责的所有元素累加到局部变量 acc 里。写法与 a1 Part B 相同，只是循环体从“写 y[i]”变成“累加 in[i]”。然后整个 block 再把 256 个 acc 合成一个数。一次循环都没进的线程，acc 保持 0，不影响结果。
  • 每个 block 只由 thread 0 写一次结果。kernel 的输出参数 dst 在第 1 遍是 ws，在第 2 遍是 out。thread 0 执行的是 dst[blockIdx.x] = s（s 是本 block 的和），是“写”不是“加”。测试会把 ws 和 out 预先填成 NaN，往里累加只会得到 NaN。
block 数不是越多越好：kMaxBlocks 的实测对比

把参考实现的 kMaxBlocks 换成不同的值，在空闲的 MI308X 上跑 shfl_bandwidth（n = 226 − 1）。同进程拷贝带宽约 2.0 TB/s，下表的百分比按它折算：

读带宽可以超过拷贝带宽：拷贝要同时读和写，而只读 kernel 实测能到 3–3.6 TB/s（§1.3）。所以更好的设计能达到甚至超过拷贝带宽。

§4.2LDS 树形归约

最经典的 block 内归约是“对折”。每个线程先把自己的值写进 LDS 数组 s[0 .. kBlock)，kBlock = 256 是 block 的线程数。然后把数组看成前后两半：前一半的每个槽位 t，加上后一半里与它相隔半个数组的槽位，结果存回槽位 t。这样一轮下来，后一半的数据都合并进了前一半。再对前一半重复同样的对折，直到只剩一个数。

每对折一层，活跃线程减半：256 个数 → 128 → 64 → … → 1，共 log₂256 = 8 层。小部件和后面几节把一层里配对的两个槽位之间的距离叫 stride，也就是这一层前一半的长度：每一层，活跃的线程 t 执行 s[t] += s[t + stride]。第一层 stride = 128，之后每层减半。哪些线程活跃、两种寻址方式有什么区别，请在下面的小部件里对照着看。小部件只画 16 个元素（相当于 kBlock = 16），规律和 256 个元素相同。

小部件只画了“每一层算什么”，没画线程之间怎么协调。写代码之前，对每一层问自己两个问题（§3.5 的思考方式）：

  • 这一层要读的槽位，是谁写的？是本线程自己，还是上一层别的线程，甚至别的 wavefront？
  • 读的时候，它一定已经写完了吗？如果不能保证，需要什么？那个东西放在哪里，才能让 block 里每个线程都执行到它，包括这一层不活跃的线程？

推荐用顺序寻址，因为它让活跃线程集中在尽量少的 wavefront 里。两种寻址的区别在于每层哪些线程活跃：

  • 顺序寻址（t < stride 的线程活跃）：活跃线程是从 0 开始连续的一段。stride ≥ 64 的那几层，每个 wavefront 要么 64 个 lane 全活跃，要么全不活跃；全不活跃的 wavefront 直接跳过这一层的加法。stride < 64 以后只剩 wavefront 0 有活，§4.3 会换一种更快的办法处理这几层。
  • 交错寻址（t % (2·stride) == 0 的线程活跃）：前几层的活跃线程分散在多个 wavefront 里。每个含有活跃 lane 的 wavefront 都要执行这一层的加法，却只有少数 lane 在干活，其余 lane 被执行掩码关掉、空等（§2.1）。到最后两层，活跃线程变少，才有 wavefront 完全不活跃。

用 256 个线程（4 个 wavefront）数一数：把每一层要执行加法的 wavefront 个数加起来，8 层合计，顺序寻址是 9 个，交错寻址是 27 个。两种写法在这里都没有 bank conflict（§3.6）：同一半个 wavefront 里的活跃 lane，读写的槽位下标互不相同，又都落在 32 个连续下标之内，所以各占一个 bank。

“全不活跃的 wavefront 直接跳过”是怎么做到的

编译器在 if 的入口生成一条条件跳转：如果这个 wavefront 的执行掩码全为 0，就跳过整个 if 体。把参考实现的 block_reduce_lds 编译成汇编，每一层的加法前面都有一条 s_cbranch_execz，就是这条跳转。

只要还有一个 lane 活跃，整个 wavefront 就得执行 if 体。所以 wavefront 的执行次数取决于“有多少个 wavefront 里至少有一个活跃 lane”，而不是活跃线程总数。

另一种交错写法会有 bank conflict

网上常见的另一种交错写法，让连续的线程处理相隔 2·stride 的槽位：

int i = 2 * stride * t;
if (i < kBlock) s[i] += s[i + stride];

它的活跃线程是连续的，wavefront 执行次数和顺序寻址一样少。但同一半个 wavefront 里相邻 lane 的地址相差 2·stride 个 float，会撞到同一个 bank。按 §3.6 的模型逐层数：stride = 1 时 2 路冲突，stride = 4、8、16 时达到 8 路冲突。顺序寻址既没有这个问题，活跃 wavefront 也少，所以是三种写法里最好的。

最后，函数返回时只要求 thread 0 拿到正确结果。这是骨架注释里的约定，因为只有 thread 0 会写 dst[blockIdx.x]。

§4.3__shfl_down 与 wave64

树形归约的最后几层很浪费。stride ≤ 64 以后，顺序寻址下只有 t < 64 的线程活跃，只剩一个 wavefront 在干活，却仍然每层都要走一遍 LDS 和屏障。同一个 wavefront 的 lane 之间有更快的通道：shuffle。它让 lane 直接读取另一个 lane 的寄存器，不需要 LDS 数组，也不需要 __syncthreads()，因为一个 wavefront 的 64 个 lane 本来就在一起执行同一条指令。

// HIP 原型（hip/amd_detail/amd_warp_functions.h）
float __shfl_down(float var, unsigned int lane_delta, int width = warpSize);

语义：每个 lane 得到“编号比自己大 lane_delta 的那个 lane”的 var。例如 __shfl_down(v, 4)：lane 0 拿到 lane 4 的 v，lane 1 拿到 lane 5 的 v，依此类推。

源 lane 超出范围时，拿回自己的 var。默认 width = warpSize = 64，所以源 lane 编号 ≥ 64 就算超出范围。例如 __shfl_down(v, 1) 在 lane 63 返回 lane 63 自己的值（本机实测）。

wavefront 里的所有 lane 都要一起调用 __shfl_down。某个 lane 不参与，别的 lane 就拿不到它的值。

width 参数：把 wavefront 分成几段

width 可以小于 warpSize。这时 64 个 lane 按每 width 个分成一段，越界在段内判断：段内编号加上 lane_delta 达到 width，就拿回自己的值。

width 必须是 2 的幂，且不超过 warpSize，本机可取 1、2、4、8、16、32、64。原因是实现里用 lane & (width − 1) 计算段内编号（hip/amd_detail/amd_warp_functions.h），width 不是 2 的幂时这个式子不成立。下面图 4.2 的 8 lane“玩具 wavefront”，可以看成 width = 8 时的一段。

ROCm 7 里，warpSize 只能在设备代码里当运行时值用：循环边界、除法、取模都可以，但不能用在需要编译期常量的地方。本机实测，constexpr int W = warpSize; 和 __shared__ float s[256 / warpSize]; 都会编译失败。前者报 “must be initialized by a constant expression”，后者报 LDS 数组不能是变长数组。

需要按 wavefront 数开 LDS 数组时，用一个编译期确定、且足够大的尺寸，再在运行时用 warpSize 决定实际用几个槽位。HIP 支持的 wavefront 宽度只有 32 和 64 两种，所以按 32 算出的槽位数一定够用。

在 AMD GPU 上，__shfl_down 由 ds_bpermute_b32 指令实现。它借用 LDS 的交叉开关在 lane 之间搬数据，但不占用你的 LDS 空间，也不需要屏障。比它更快的跨 lane 指令（DPP）会在后面的 Lab 中遇到。

§4.4block 级 shuffle 归约

shuffle 只能在一个 wavefront 内部用。一个 256 线程的 block 有 256 ÷ 64 = 4 个 wavefront，要合成一个数，还需要一次跨 wavefront 的汇总。这又要用 LDS，但只需要一个很小的数组和一次屏障：

  1. 每个 wavefront 各自做 wavefront 内归约（§4.3），lane 0 拿到本 wavefront 的和。
  2. 每个 wavefront 的 lane 0 把结果写进 LDS 数组的第 wave_id 个槽位。
  3. __syncthreads()：保证所有 wavefront 都写完了。
  4. 第 0 个 wavefront 读回这些部分和：lane k 读第 k 个槽位。槽位只有 wavefront 数个（这里是 4 个），所以 k ≥ 4 的 lane 没有对应的槽位，必须用 0，否则会把垃圾值加进来。然后第 0 个 wavefront 再做一次 wavefront 内归约。

其中线程的 wavefront 编号和 lane 编号这样算（一维 block）：

wave_id = threadIdx.x / warpSize
lane = threadIdx.x % warpSize
wavefront 数 = blockDim.x / warpSize

最后一步（wavefront 0 内部再归约）要求 wavefront 0 的全部 64 个 lane一起调用 shuffle：缺了源 lane，shuffle 就拿不到数据。所以“读 LDS 或补 0”可以放在 if 里，但调用 wavefront 内归约那一步，整个 wavefront 0 都要参与。

两种做法各要几次屏障

参考实现的树形归约执行 1 + 8 = 9 次 __syncthreads()：写入 LDS 后 1 次，8 层每层之后各 1 次。约定只要求 thread 0 拿到结果，而最后一层只有 thread 0 写 s[0]、也只有它读，所以最后那一次可以省掉，变成 8 次。block 级 shuffle 归约只有写部分和之后的 1 次。

§4.5浮点求和误差与为什么测试用全 1 输入做精确比较

浮点加法不满足结合律：(a + b) + c 与 a + (b + c) 可能差最后几位。原因是每次加法都要把结果舍入到 24 位有效数字，这是 fp32 的精度。CPU 参考实现按顺序一个个加，你的 GPU 实现先分块、再树形合并，求和顺序完全不同，结果自然有微小差异。

所以随机输入的比较要允许舍入误差。测试的条件是 |GPU 结果 − 参考值| ≤ 1e-5 · Σ|x| + 1e-6，参考值在 CPU 上用 double 累加。容差按输入的绝对值之和 Σ|x| 缩放，而不是按结果本身：正负数相消、和接近 0 时，按结果缩放的容差会小到误判正确的实现。

但容差有个弱点：漏加或多加一个元素，误差可能小到藏在容差里。于是测试另外用全 1 输入做精确比较。原理是：fp32 能精确表示 0 到 224 之间的每一个整数。全 1 输入的所有部分和都是不超过 n 的整数，n < 224 时每一步加法都没有舍入，所以不管按什么顺序加，结果都恰好等于 n。漏掉或重复一个元素，结果就差 1，立刻暴露。

224 = 16777216 往上，相邻两个 fp32 的间距变成 2。这时 16777216 + 1 的精确结果 16777217 不可表示，要舍入到最近的可表示数。它正好在 16777216 和 16777218 中间，IEEE 754 规定这种情况取二进制有效数字最后一位为 0（偶数）的那个。顺着这个思路，你能推出“单线程从 0 开始对 225 个 1 顺序累加”的结果吗？（a3 书面问题 2。）

对全 1 这样的输入，分块让每个线程累加的 1 少得多，部分和远小于 224，就碰不到上面说的舍入问题。对一般输入，误差还取决于数值本身和合并顺序，分块不保证误差一定更小：例如 [224, −224, 1, 0] 顺序相加得 1，分成 [224, 1] 和 [−224, 0] 两组再合并却得 0。

用例 repeatable_output 连续调用两次，按容差比较两次的结果，主要检查你有没有把结果累加到上一次的 out 上。它不检查两次是否逐位相同。不过骨架的两遍结构本身是可重复的：每个 block 的线程负责哪些元素、按什么顺序合并都是固定的，只要没有数据竞争，两次结果应当完全一样。

如果改用原子加 atomicAdd（见下方提示框）把各 block 的部分和加到同一个地址，block 完成的先后每次不同，浮点结果就可能每次差一点。这是以后写跨 block 归约时要权衡的。

float atomicAdd(float* addr, float val); 在设备代码里把 val 加到 *addr 上。“读—加—写”三步作为一个不可分割的整体完成，返回加之前的旧值。int、unsigned 等类型也有同名重载。

多个线程（可以来自不同 block）对同一地址做 atomicAdd 时，硬件把它们一个接一个地执行，所以不会丢失任何一次加法，但先后顺序不确定。同一地址上的原子操作越多，串行得越久。它是后面 Lab 里跨 block 同步（计数器、标志位）的基本工具。本 Lab 只在 a3 书面问题 4 里用到它，作业代码不需要。

§5GEMM

矩阵乘 C[M×N] = A[M×K] · B[K×N]，即 GEMM（General Matrix Multiply），是深度学习里最重要的 kernel，也是本课的收官。它综合了合并访存、LDS、同步和 bank conflict，还引出一个新主题：数据复用。本节所有矩阵都是行主序（每一行在内存里连续存放）的 fp32。

§5.1naive GEMM 与线程到输出的映射

C 的每个元素是 A 的一行与 B 的一列的点积：

C[i][j] = Σk=0..K−1 A[i][k] · B[k][j]　　// 行主序偏移：A[i·K + k]，B[k·N + j]，C[i·N + j]

最直接的并行方式是每个线程负责 C 的一个元素：在寄存器里累加 K 次乘加，最后写一次 C。a4 的 launch_gemm_naive 已经给出启动配置：block(64, 4)，grid 的 x 方向覆盖 N、y 方向覆盖 M。所以 x 方向的全局坐标是列号 j，y 方向的是行号 i。

为什么这样分配？用 §3.1 的标准检查一个 wavefront（同一个 i，连续 64 个 j）在第 k 次循环中的访问：

  • A[i·K + k]：64 个 lane 读同一个地址，只涉及一条 cache line，硬件把数据广播给所有 lane。
  • B[k·N + j]：j 连续 → 地址连续 → 合并。
  • 最后写 C[i·N + j]：同样连续，合并。

反过来让 x 方向对应 i，读 A 和写 C 都会变成相隔一整行的跨步访问。和转置一样，要让 x 方向（相邻 lane）沿着内存连续的方向走。另外别忘了 i、j 的边界检查（M、N 都可能不是 64、4 的倍数），以及 K 可能等于 1。

衡量 GEMM 用 GFLOPS，即每秒十亿次浮点运算。一次乘加算 2 次浮点运算，整个 GEMM 共 2·M·N·K 次，除以耗时即可。M = N = K = 2048 时是 2 × 20483 ≈ 172 亿次。

§5.2计算强度与数据复用

按 §1.4 的方法估算 naive GEMM 的计算强度。每次乘加（2 FLOP）要读 1 个 A 元素和 1 个 B 元素，共 8 字节。如果这些读取全部来自显存，强度只有 2 ÷ 8 = 0.25 FLOP/B，在图 1.3 中远在交点（约 7）左边。即使显存带宽全用上，也只有 5.3 TB/s × 0.25 ≈ 1.3 TFLOPS。

可是 GEMM 本身并不需要这么多访存。A 的每个元素要参与 N 次乘加（和 B 的每一列各一次），B 的每个元素要参与 M 次。naive 实现每次用到都重新读一遍，程序里没有安排任何复用。它能跑多快，取决于硬件对同地址请求的合并和缓存命中。这些不受程序控制，规模一变就可能失效。

naive GEMM 的实测速度说明了什么、没说明什么

本机实测 naive 约 1150 GFLOPS，即每秒约 5750 亿次乘加。按每次乘加读 8 字节计，相当于每秒约 4.6 TB 的读取量，比 HBM 理论带宽 5.3 TB/s 低不了多少，也比实测拷贝带宽高。

但这是按线程逐个计数的“逻辑”读取量。同一 wavefront 读同一个 A 地址只发一次请求，很多读取又命中了缓存，所以它不等于实际的 HBM 流量。它说明 naive 实现确实得到了硬件的不少帮助，却不能用来量化缓存的贡献：拷贝带宽按读 + 写计算，访问模式也不同，两者不能直接比。要知道实际 HBM 流量，需要用性能计数器剖析。

分块（tiling）让复用由程序保证：一个 block 负责 C 的一个 BM × BN 的子块。计算这个子块需要 A 的 BM 行（一个“行块”）和 B 的 BN 列（一个“列块”）。沿 K 方向把它们切成长度为 BK 的若干段，每一段：

  • 从显存读入 A 的 BM × BK 小块和 B 的 BK × BN 小块，放进 LDS；
  • block 内的线程从 LDS 里反复读它们，完成 BM × BN × BK 次乘加。

算一下复用的效果。以 BM = BN = BK = 16 为例：每一段读入 16 × 16 + 16 × 16 = 512 个 float，即 2 KiB；完成 16 × 16 × 16 = 4096 次乘加。平均每次乘加只需 2048 ÷ 4096 = 0.5 字节显存读取，比 naive 的 8 字节少了 16 倍。（a4 书面问题 1 请你对 TILE = 32，即 BM = BN = BK = 32，做同样的计算。）

一般地，每次乘加需要的显存字节数与子块边长成反比：子块越大，复用越多。子块大小的上限来自 LDS 容量、寄存器数量，以及“block 数要足够多才能填满 80 个 CU”。

§5.3LDS 分块与 K 方向循环、两次同步

分块 kernel 的骨架是一个沿 K 方向的循环。每一轮先让 block 的线程协作把这一段的小块搬进 LDS，再让每个线程从 LDS 里反复读、做乘加，然后进入下一轮。这个“加载 → 同步 → 计算 → 同步”的节奏在很多 kernel 里都会出现。下面用一个更简单的一维问题演示它：对每个 x[i]，求它与所有 p[j] 的绝对差之和。它不是 GEMM，但节奏完全一样：

constexpr int kT = 256;   // block 大小 = 每段 tile 的长度
// y[i] = Σ_j |x[i] − p[j]|：每个 x[i] 都要和全部 m 个点 p[j] 比较（“全对全”）
// 每个 p[j] 被 block 内 256 个线程各用一次 → 先搬进 LDS，再让大家复用
__global__ void sum_dist(const float* x, int n, const float* p, int m, float* y) {
  __shared__ float tile[kT];
  const int i = blockIdx.x * kT + threadIdx.x;
  const float xi = (i < n) ? x[i] : 0.0f;    // 越界线程也留下来：它要帮忙搬数据、参加屏障
  float acc = 0.0f;
  for (int j0 = 0; j0 < m; j0 += kT) {
    if (j0 + threadIdx.x < m) tile[threadIdx.x] = p[j0 + threadIdx.x];   // 协作加载（合并）
    __syncthreads();                                                      // 屏障 ①
    const int cnt = min(kT, m - j0);                                      // 最后一段可能不满
    for (int k = 0; k < cnt; ++k) acc += fabsf(xi - tile[k]);            // 用整段 tile
    __syncthreads();                                                      // 屏障 ②
  }
  if (i < n) y[i] = acc;
}
  • 协作加载：每个线程只搬 tile 中的一个元素，却要读整段 tile，这就是复用。相邻线程读相邻的全局地址，合并（§3.1）。GEMM 里每一段要搬两个二维小块，线程数与小块的元素数也未必相等。搬运的分工要你自己设计：哪个线程搬哪个元素、是否要循环搬多个（参考 §3.4），同样要保证合并。
  • 屏障 ①（写后读）与转置中的同步作用相同：读 tile 之前，别的线程负责的那部分必须已经写进去了。
  • 屏障 ②（读后写）是新出现的。下一轮一开始就要往 tile 里写下一段的数据。如果某个快的 wavefront 已经进入下一轮开始覆盖，而慢的 wavefront 还在读这一段，慢的那个就会读到被覆盖的值。所以覆盖之前要等所有人用完，这叫读后写（write-after-read）依赖，和屏障 ① 解决的“写后读”正好相反。把屏障 ② 删掉，结果会随调度时好时坏，而且在本机上“坏”的概率小到测试几乎抓不到（见 §5.4 末尾的“判分抓不到的两种 bug”），只能靠你自己保证它在。
  • 越界线程不能提前 return。注意代码里 i ≥ n 的线程并没有退出：它们不产生结果，但要帮忙把 p 搬进 tile，并且要执行两个屏障。两个屏障都在循环体的“顶层”，不在任何只有部分线程进入的 if 里（§3.5）。
  • 这个例子用 cnt 处理最后一段不满的情况。GEMM 还有另一种办法：加载时把越界元素补成 0，§5.4 会讲。两种都可以。

别忘了检查 LDS 读的 bank conflict（§3.6）。在你设计的内层循环里，写出同一个 wavefront 的 64 个 lane 在同一步读的 LDS 地址：读同一个地址是广播，不冲突；读连续地址也不冲突；按固定跨步读，就要用 §3.6 的公式算一算，必要时加 padding。

§5.4每线程多个输出、边界补零

每线程多个输出（寄存器分块）

“每线程一个输出”的分块版本有一个新瓶颈：内层循环每做 1 次乘加，就要从 LDS 读 2 个数。LDS 虽快，也有带宽上限，而且读 LDS 本身要占用指令。解决办法是把 §5.2 的复用思路再往下推一层，从 LDS 推到寄存器：

让每个线程负责 C 子块中的 TM × TN 个元素，用 TM × TN 个寄存器累加器。内层循环的每一步 kk：从 LDS 读 TM 个 A 值和 TN 个 B 值到寄存器，然后做 TM × TN 次乘加。每次乘加要读的 LDS 数据从 2 个降到 (TM + TN) ÷ (TM × TN) 个，例如 TM = TN = 4 时是 8 ÷ 16 = 0.5 个。

设计时要同时考虑几件事，没有唯一答案：

  • 子块与线程数的关系：block 的线程数 × 每线程输出数 = BM × BN。例如 256 个线程、每线程 4 × 4 个输出，就能负责 64 × 64 的子块。
  • 输出怎么分给线程：一个线程的 TN 个输出如果是连续的几列，相邻线程写 C 时会相隔 TN 个元素。如果是每隔“x 方向的线程数”列取一列（类似 grid-stride loop 的分法），相邻线程写的就是相邻地址。两种都能算对，合并程度不同。
  • 资源：累加器占寄存器，As + Bs 占 LDS。例如 BM = BN = 64、BK = 16 时，LDS 用量是 (64 × 16 + 16 × 64) × 4 字节 = 8 KiB。占用太多会降低 occupancy（§2.4）。

让累加器真的留在寄存器里

TM × TN 个累加器在 C++ 里自然写成一个小数组 float acc[TM][TN]。最好让访问 acc 的下标在编译期确定，并把访问它的循环展开：这样编译器最容易把每个元素分配到一个固定的寄存器里。

下标或循环边界在编译期未知时，结果取决于编译器。数组可能仍留在寄存器里，由“运行时再挑选用哪个寄存器”的指令访问，这比直接访问慢；也常常被放进 scratch（每个线程私有的一块显存，经缓存访问），这样每次乘加都变成一次访存，结果仍然正确，只是慢很多，判分只会告诉你“性能 FAIL”。到底是哪种，要用下文的资源报告确认。要让编译器确定下标，需要两件事：

  • TM、TN 和访问 acc 的循环边界都是编译期常量，例如 constexpr int TM = 4;。不要用 kernel 参数或其他运行时变量当边界。
  • 访问 acc 的循环被完全展开。展开就是编译器把循环体按次数复制多份，每份里的 i、j 换成字面常数，于是访问变成 acc[0][0]、acc[0][1]……边界是常量的小循环在 -O2 下通常会自动展开；在循环前写 #pragma unroll 可以明确要求展开。
constexpr int TM = 4, TN = 4;
float acc[TM][TN] = {};          // 别忘了初始化为 0
// ……在内层循环里：
#pragma unroll
for (int i = 0; i < TM; ++i)     // 常量边界 + 展开：有利于 acc 留在寄存器（以资源报告为准）
#pragma unroll
  for (int j = 0; j < TN; ++j)
    acc[i][j] += a[i] * b[j];
// 反例：for (int i = 0; i < tm; ++i) …   ← tm 是运行时的值，可能展不开，acc 可能进 scratch（检查资源报告）

怎么确认？编译时加上 -Rpass-analysis=kernel-resource-usage，hipcc 会为每个 kernel 打印寄存器、scratch 和 LDS 用量。在 lab1-hip-basics/ 下运行：

/opt/rocm/bin/hipcc -std=c++20 -O2 --offload-arch=gfx942 -c a4-gemm/gemm.hip -o /tmp/gemm.o \
    -Rpass-analysis=kernel-resource-usage

重点看两行。ScratchSize 不为 0，说明有数据放进了 scratch。VGPRs Spill 不为 0，说明寄存器不够用，编译器把一部分值“溢出”到了 scratch，累加器开得太多时会出现。对分块 GEMM，这两项都应该是 0。出现 scratch 时，检查 acc 的下标和循环边界是否为编译期常量，以及寄存器用量。

LDS Size 是每个 block 的 LDS 用量。Occupancy [waves/SIMD] 是编译器估算的每个 SIMD 最多驻留的 wavefront 数（§2.4）。编译器不知道你启动时用多大的 block，默认按最大的 1024 线程估算 LDS 的限制，结果可能偏高。例如一个用 48 KiB LDS 的 kernel，编译器报 4；在 kernel 前加 __launch_bounds__(256) 告诉它 block 是 256 线程后，报 1。按 256 线程启动时，每个 CU 只放得下 1 个这样的 block，每个 SIMD 1 个 wavefront，后者才对（本机实测，见 §2.4 的折叠框）。

边界补零

M、N、K 都可能不是子块尺寸的倍数，测试里有 17 × 33 × 65、500 × 300 × 257，还有 1 × 1 × 1。最省心的处理方式是在加载时补零：协作加载时，若要读的 A[i][k] 或 B[k][j] 落在矩阵之外，就往 LDS 里写 0。0 参与乘加不改变结果，于是：

  • 内层乘加循环不需要任何边界判断，K 方向最后一段不满也照常循环 BK 次；
  • 边界判断只出现在两处：加载（越界读 → 存 0）和最后写 C（越界的 (i, j) 不写）；
  • 屏障仍然在所有 if 之外。

M = N = K = 2048，要求 GFLOPS 达到同进程实测 fp32 FMA 吞吐的 6.5%，空闲时约 1740 GFLOPS。和 a2、a3 用拷贝带宽作基准是同一个思路：基准是一个纯寄存器 FMA 微基准（§1.3 表中那种，空闲时约 27–28 TFLOPS），测试把你的 kernel 和它交替计时。别人在同一张卡上跑东西时两者一起变慢，比值大体不变。

空闲 MI308X 上的参考数字：naive 约 1150 GFLOPS（约 4.3%）；每线程 1 个输出的 16 × 16 分块约 3100（约 11.5%）；参考实现约 4600（约 17%），它是一个简单设计，每线程算几个输出。认真做过寄存器分块的 GEMM 可达约 9500 GFLOPS，也只是实测 fp32 吞吐的三分之一左右。所以 4600 只是“过线有余”的参考，远不是上限。一个正确、访存合并、两个屏障都在的基础分块版本就能过线，寄存器分块是继续提速的主要手段。

正确性按逐元素误差界判定：|C − ref| ≤ 1e-5 · Σ|a·b| + 1e-6，ref 是 CPU 上用 double 算的参考值。这个容差针对本课的随机输入和规模，给常见的 fp32 实现留了很大余量，K 方向怎么分段、按什么顺序求和都可以。它不是对所有输入、所有求和顺序都成立的误差保证。

为什么说这个容差不是普遍的保证

可以构造出一个按顺序正确累加、却超出容差的例子。取 K = 512，乘积依次是 1 和 511 个 2−25。fp32 在 1 附近的间距是 2−23，1 + 2−25 会舍入回 1，所以顺序累加的 fp32 结果一直是 1。精确结果是 1 + 511 × 2−25 ≈ 1.0000152，误差约 1.52 × 10−5；容差是 1e-5 × 1.0000152 + 1e-6 ≈ 1.10 × 10−5，被超过了。

测试用的是 [−1, 1) 里的随机数。对本课常见的 fp32 实现，舍入误差通常会部分抵消，典型误差远小于容差。这是经验现象：输入范围和随机性本身并不保证不超出容差，在 [−1, 1) 里同样能构造出类似上面的反例。

有两类错误在本机上几乎不会让测试失败，只能靠你自己推理排除：

① 漏掉屏障 ②（§5.3 的读后写）。实测把它删掉的分块 GEMM，在所有用例上反复运行都“碰巧”算对。但它仍然是数据竞争，换个尺寸、换个负载、换个编译器版本就可能出错。

② 累加器没有初始化。float acc[TM][TN]; 不写 = {} 是未定义行为，编译器这次恰好当成 0，下次未必。

“全部 OK”不能证明没有这两个问题。写完后对照 §5.3 逐条检查。

§5.5展望：MFMA（Lab 4）

到目前为止，所有乘加都由向量单元完成：每个 lane 每次算一个 fp32 FMA，用 packed 指令（§1.3）时算两个。CDNA3 的每个 CU 里还有专门的矩阵核心（Matrix Core），通过 MFMA（Matrix Fused Multiply-Add）指令使用。一条 MFMA 指令由整个 wavefront 协作，直接完成一个小矩阵乘（例如 32 × 32 × 8），操作数和结果分布在 64 个 lane 的寄存器里。

对 fp32，CDNA3 的矩阵峰值与向量峰值相同（MI300X 都是 163.4 TFLOPS）。MFMA 的威力在低精度：fp16 和 bf16 是两种 16 位浮点格式，按 MI300X 数据表的 fp16 / bf16 稠密峰值 1307.4 TFLOPS 折算，每 CU 每周期 2048 FLOP，是 fp32 向量峰值（每 CU 每周期 256 FLOP，§1.3）的 8 倍。代入本机的 80 个 CU 和最高频率 1.85 GHz，得 80 × 2048 × 1.85 GHz ≈ 303 TFLOPS。这是理论值，和 fp32 一样要打频率折扣：本机实测 bf16 MFMA 约 230 TFLOPS，运行频率约 1.4 GHz。

Lab 4 会把本节的分块结构原封不动地搬过去：行块 × 列块、K 方向循环、LDS 中转、两次同步，只是把最内层的标量乘加换成 MFMA。所以现在把分块想透，后面会轻松很多。
