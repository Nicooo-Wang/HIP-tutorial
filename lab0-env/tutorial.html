Lab 0：环境与工具

Lab 0 · 环境与工具

从 make grade 到第一个 kernel

这一课不追求性能，只做三件事：熟悉“改代码 → 判分 → 读失败信息 → 再改”的工作循环；写出并启动你的第一个 GPU kernel；用 HIP API 亲手查出这台 MI308X 的关键数字。之后每一课都建立在这些习惯和数字之上。

预计阅读 40 分钟 · 对应 Assignment a1、a2

§1.3读懂判分输出

拿到仓库后先什么都不改，直接运行一次 make grade A=a1。你会看到类似这样的输出（这是骨架原样的真实结果）：

使用 GPU: HIP_VISIBLE_DEVICES=7
a1-hello
  one_block_exact............................. FAIL (0/1)
    n=256: 256/256 个元素错误，首个错误在 [0]：期望 0，得到 -1
  single_element.............................. FAIL (0/1)
    n=1: 1/1 个元素错误，首个错误在 [0]：期望 0，得到 -1
  not_multiple_of_block....................... FAIL (0/2)
    n=1000: 1000/1000 个元素错误，首个错误在 [0]：期望 0，得到 -1
    n=257: 257/257 个元素错误，首个错误在 [0]：期望 0，得到 -1
  many_blocks................................. FAIL (0/2)
    n=4194307: 4194307/4194307 个元素错误，首个错误在 [0]：期望 0，得到 -1
Score: 0/6

逐行读：

  • 第一行：判分脚本自动挑了一张最空闲的 GPU（机器是多人共享的，见 §6.2）。
  • 用例行：用例名 + 结果 + 得分。用例名本身就是提示——not_multiple_of_block 说明这个用例专门测“n 不是 block 大小整数倍”的情形。用例的具体内容在同目录的 test.cpp 里，随时可以打开看。
  • 缩进的说明行：哪个规模（n=1000）、错了多少个元素、第一个错在哪个下标、期望值和实际值。

“得到 -1”是个重要线索：测试在调用你的代码之前，先把输出缓冲区全部填成 -1。如果某个位置仍是 -1，说明根本没有线程写过它；如果是别的错误值，说明写了但写错了。这两种情况的排查方向完全不同。

还有一类失败信息长这样：

  not_multiple_of_block....................... FAIL (0/2)
    越界写：缓冲区（1000 个元素）之后的哨兵区被改写（距边界 1 字节）

测试给每个缓冲区的前后各多分配了 256 KiB 的“哨兵区”，整块填满同一个特殊的 32 位值（它是一个 NaN；当作 int 读则是一个约 21 亿的大数）。kernel 结束后逐字节检查哨兵区：若被改写，说明你的代码写到了数组范围之外。反过来，如果代码越界读到了哨兵值，这个值一旦参与运算（哪怕乘以 0）就会把结果变成 NaN 或明显错误的大数，在逐元素比较时暴露出来。

另外两种失败信息：“超时（>60 s）”通常是死循环或挂起；“进程崩溃（退出码 …）”后面会附上程序最后输出的几行，一般能看到 HIP 报出的错误原因（§4 会讲怎么看）。

§1.4用 make run 调试

make grade 把每个用例放在独立进程里跑、只汇总结论。想看程序自己的输出（比如你加的 printf）时，用 make run：

make run A=a1                      # 编译并直接运行全部用例，输出原样打印
make run A=a1 CASE=single_element  # 只运行一个用例

两个命令背后都是同一条编译命令（STUDENT_SRC 告诉 test.cpp 要包含哪个 .hip 文件；common/lab.mk 里实际写的是绝对路径，效果与下面相同）：

/opt/rocm/bin/hipcc -std=c++20 -O2 --offload-arch=gfx942 -I../common \
  -DSTUDENT_SRC="\"$PWD/a1-hello/hello.hip\"" a1-hello/test.cpp -o build/run-a1

hipcc 是 ROCm 的编译器驱动，一次编译同时生成 CPU 代码和 GPU 代码；--offload-arch=gfx942 指定 GPU 代码的目标架构，即本机 MI308X（§2）。编译出的程序在 build/run-a1，之后可以直接重复运行它，或者交给 §6 的工具分析。kernel 里也可以用 printf，但成千上万个线程会一起打印，记得只让少数线程打印，例如加上 if (i == 0)。

每个 Assignment 的 README 末尾有几道书面问题，答案写在 lab0-env/answers.md。它们不计分，但都是后面几课要用到的直觉，建议认真写。

§2一台 MI308X 长什么样

写 kernel 之前，先对“代码会跑在什么东西上”有个画面。本机有 8 张 AMD Instinct MI308X，架构代号 gfx942，属于 CDNA3 架构（与 MI300X 同代）。

§2.1从 GPU 到 SIMD

MI308X 是由多块芯粒（chiplet）拼成的。负责计算的芯粒叫 XCD（Accelerator Complex Die）。本机每张卡有 4 个 XCD；每个 XCD 里有若干 CU（Compute Unit，计算单元）和一块所有 CU 共享的 L2 缓存。CU 是 GPU 上独立调度执行的基本单位，每个 CU 内部又有 4 个 SIMD 执行单元，以及一块 CU 内共享的高速片上存储 LDS（Local Data Share）。

你在网上查到的 CDNA3 资料多数是 MI300X：它有 8 个 XCD、每个 XCD 启用 38 个 CU，共 304 个 CU。本机的 MI308X 是 4 个 XCD、共 80 个 CU。所以不要照抄网上的数字——Assignment a2 会让你用 API 把本机的数字查出来。

§2.2软件层次如何落到硬件上

写 kernel 时，你描述的是一个三层的“线程组织”：一次 kernel 启动产生一个 grid；grid 由许多 block 组成；每个 block 由许多 thread 组成。硬件运行时，再把 block 内的线程每 64 个打包成一个 wavefront，这 64 个线程同时执行同一条指令（这是编程模型层面的说法：物理上每个 SIMD 每周期处理 16 个 lane，一条 wave64 的向量指令分 4 个周期发完）。

§3第一个 kernel

§3.1kernel 与启动语法

kernel 是一个在 GPU 上、由大量线程同时执行的函数。它和普通 C++ 函数有三点不同：

  • 用 __global__ 修饰，返回类型必须是 void（结果通过指针写回显存）。
  • 由 CPU（称为主机，host）上的代码用 <<<grid, block>>> 语法启动，尖括号里写“启动多少个 block、每个 block 多少个线程”。
  • 函数体被每一个线程各执行一遍。线程靠内置变量区分“我是谁”：threadIdx.x（我在 block 内的编号）、blockIdx.x（我所在 block 的编号）、blockDim.x（每个 block 有多少线程）。

下面这个例子只启动 1 个 block、64 个线程，给一个长度恰好为 64 的数组每个元素加 1：

#include <hip/hip_runtime.h>

// __global__：在 GPU 上执行、由主机启动的函数
__global__ void add_one(int* data) {
  int t = threadIdx.x;      // 本线程在 block 内的编号：0, 1, ..., blockDim.x - 1
  data[t] = data[t] + 1;    // 64 个线程各改一个元素，同时进行
}

// 主机端函数：data 指向 GPU 显存，长度恰好为 64
void add_one_64(int* data, hipStream_t stream) {
  //       grid  block  动态LDS  stream
  add_one<<<1,    64,    0,       stream>>>(data);
}

尖括号里的 4 个参数依次是：block 个数（grid 大小）、每个 block 的线程数、动态分配的 LDS 字节数（本课用不到，填 0）、在哪个 stream 上执行。stream 可以理解为“GPU 任务队列”；传 nullptr（也就是 0）表示默认队列。a1 的测试调用你的函数时就传入 nullptr，你只需把收到的 stream 原样传给启动语句。

blockIdx、threadIdx 等都有 .x/.y/.z 三个分量，用来方便地处理二维、三维数据（Lab 1 会用到）。本课只用 .x，其余分量默认为 0、大小为 1。

§3.2全局下标与边界检查

上面的例子只有一个 block，threadIdx.x 就足以区分所有线程。但一个 block 最多 1024 个线程，处理四百万个元素必须用很多个 block——而每个 block 里的 threadIdx.x 都从 0 开始重新编号。只用 threadIdx.x 的话，所有 block 会争抢同样的前 blockDim.x 个元素，后面的元素没人管。

解决办法和给楼里的房间统一编号一样：第 b 栋楼、每栋 B 间、楼内第 t 间，全局编号就是“前面 b 栋楼的房间总数”加上“楼内编号”：

全局下标 = blockIdx.x × blockDim.x + threadIdx.x

这样 grid 中每个线程都有一个独一无二的全局下标 0, 1, 2, …，正好可以用来对应数组的每个元素。

第二个问题：block 大小固定（例如 256），而 n 是任意的。只要 n 不是 256 的整数倍，启动的线程总数就会多于 n，多出来的那些线程算出的全局下标 ≥ n——它们对应的元素根本不存在。这些线程必须什么都不做：在写内存之前先判断下标是否在 [0, n) 范围内，不在就跳过。这就是边界检查。漏掉它，多出来的线程就会写到数组末尾之后的内存里（图 1.2 的哨兵区就是来抓这个的）。

在下面的小部件里调整 block 大小和 n，点任意一个线程格子，看它算出的全局下标；灰色格子是下标越界、必须被边界检查挡住的线程。

§3.3grid 要多大：向上取整

每个 block 负责 B = blockDim.x 个元素，要覆盖全部 n 个元素，block 个数必须至少是 n / B，并且向上取整：⌈n / B⌉。例如 n = 1000、B = 256：1000 / 256 = 3.9…，需要 4 个 block（共 1024 个线程，其中 24 个越界、什么都不做）。

陷阱在于 C++ 的整数除法是向下取整的：1000 / 256 的结果是 3，3 个 block 只有 768 个线程，最后 232 个元素没人写。在小部件 3.1 中勾选“错误示范”就能看到这种情形；n < B 时更糟——grid 变成 0，启动直接报错 hipErrorInvalidConfiguration。

只用整数运算（不借助浮点和 ceil）也能求 ⌈a / b⌉（a ≥ 0，b > 0）。常用的技巧是：做整数除法之前，先给分子 a 加上一个合适的常数。这个常数该是多少？请你自己推出来，判断标准有两条：

  • a 恰好是 b 的整数倍时，加上它之后整数除法的结果不能变；
  • a 比某个整数倍多出哪怕 1 时，加上它之后结果要恰好多 1（“进一位”）。

想清楚“余数最小是几、最大是几”就能确定这个常数。推出来后用几组数验算：b = 256 时，a = 1、256、257、1000、1024 应分别得到 1、1、2、4、4。小部件 3.1 的读数也可以帮你核对。

a1 的 many_blocks 用例用 n = 4194307（= 222 + 3）——比 256 的整数倍多 3，专门检查“最后一个不满的 block”有没有被启动。

让 launch_fill_ids(out, n, stream) 结束后 out[i] == i 对所有 0 ≤ i < n 成立：补全 kernel 中的全局下标与边界检查（TODO a1-1，§3.2），以及启动时的 grid 大小（TODO a1-2，§3.3）。n 可能是 1、不整除 256、或四百万以上。

本节对应 Assignment a1，任务说明与提示见 lab0-env/a1-hello/README.md。

§4错误检查

§4.1每个 HIP API 都返回 hipError_t

几乎所有 HIP 运行时函数（hipMalloc、hipMemcpy、hipDeviceSynchronize……）的返回值都是 hipError_t。成功时为 hipSuccess，否则是某个错误码，可以用 hipGetErrorString(err) 转成可读的说明。忽略返回值时 hipcc 会给出警告：

warning: ignoring return value of type 'hipError_t' declared with 'nodiscard' attribute

不要无视这类警告：GPU 出错时程序往往不会立刻崩溃，而是带着错误的结果继续跑下去，直到很远的地方才露馅。

§4.2kernel 是异步的

启动 kernel 的那一行不会等 kernel 跑完：主机只是把任务放进 stream 队列就立刻返回，继续执行后面的代码；GPU 在后台执行。想等它结束，要调用 hipDeviceSynchronize()，它会阻塞主机线程，直到本进程在当前设备上（所有 stream 中）之前提交的工作全部完成——它不会去等别的进程在同一张卡上的任务。

异步带来一个后果：kernel 的错误分两类，暴露的时机不同。

  • 启动错误：例如 block 大小超过 1024，或 grid 为 0。kernel 根本没有开始跑。启动语句本身没有返回值，要紧接着调用 hipGetLastError() 取出这个错误（本机实测返回 hipErrorInvalidConfiguration；用 hipGetErrorString 转成文字是 invalid configuration argument，判分输出里看到的就是这句）。
  • 执行错误：例如访问了非法地址。要等 kernel 真正执行时才发生，所以要到 hipDeviceSynchronize() 的返回值里才能看到（本机实测为 hipErrorIllegalAddress。部分情况下——例如地址远远超出合法范围——运行时还会在终端打印一段 HSA_STATUS_ERROR_… 诊断，其中有出错的 kernel 名字；但常见的越界访问往往只有这个错误码，终端上什么也不打印）。

只越界一点点（比如写到数组末尾之后几个元素）通常不会触发非法地址错误——那块内存属于你的进程，写进去也“合法”，只是破坏了别的数据。所以“程序没报错”不等于“没有越界”。本机实测甚至有更极端的情况：往空指针附近的地址写，hipDeviceSynchronize() 也返回 hipSuccess。hipSuccess 永远不能证明访存是合法的。

§4.3HIP_CHECK 宏

每次都手写 if (err != hipSuccess) … 太啰嗦，惯用做法是写一个宏：执行表达式，失败时打印“哪个调用、在哪个文件哪一行、什么原因”，然后退出。课程的公共头文件 common/harness.hpp 已经提供了 HIP_CHECK，它大致是这样的：

#define HIP_CHECK(expr)                                                  \
  do {                                                                   \
    hipError_t err_ = (expr);                                            \
    if (err_ != hipSuccess) {                                            \
      std::fprintf(stderr, "HIP 错误: %s\n  位置 %s:%d\n  原因 %s\n",      \
                   #expr, __FILE__, __LINE__, hipGetErrorString(err_));  \
      std::exit(2);                                                      \
    }                                                                    \
  } while (0)

#expr 把被检查的代码原样变成字符串，__FILE__/__LINE__ 给出位置；do { … } while (0) 让宏在 if 语句中使用时也不出错。典型用法（以一个假想的 my_kernel 为例）：

float* d_x = nullptr;
HIP_CHECK(hipMalloc(&d_x, n * sizeof(float)));
my_kernel<<<grid, block, 0, stream>>>(d_x, n);
HIP_CHECK(hipGetLastError());        // 启动错误在这里暴露
HIP_CHECK(hipDeviceSynchronize());   // 执行错误在这里暴露
HIP_CHECK(hipFree(d_x));

在 Assignment 的 .hip 文件中可以直接使用 HIP_CHECK：测试程序 test.cpp 在包含你的文件之前已经包含了 harness.hpp。a1 不需要它（测试会替你同步和检查），a2 的每个查询都应该用它包起来。

§5查询设备属性

硬件参数不应该凭记忆写死在代码里：同一份代码可能跑在 MI300X（304 CU）、MI308X（80 CU）或别的卡上。HIP 提供两种查询方式。

§5.1hipGetDeviceProperties：一次拿到整张“属性表”

hipGetDeviceProperties(&prop, device) 把第 device 号 GPU 的几十项属性一次性填进一个 hipDeviceProp_t 结构体。它的成员定义在 /opt/rocm/include/hip/hip_runtime_api.h，多数成员后面有英文注释说明含义，其中一部分注明了单位（例如 totalGlobalMem 写了 in bytes，clockRate 写了 in khz）。例如：

hipDeviceProp_t prop;
HIP_CHECK(hipGetDeviceProperties(&prop, 0));
std::printf("名字: %s\n", prop.name);                        // 字符数组，如 "AMD Instinct MI308X"
std::printf("L2: %d 字节\n", prop.l2CacheSize);               // int
std::printf("每 CU 最多线程数: %d\n", prop.maxThreadsPerMultiProcessor);

注意成员的类型：表示内存容量的成员（如 totalGlobalMem，单位字节）是 size_t，本机的值约 2×1011，超出了 int 的范围，存放时要用 64 位整数类型。

§5.2hipDeviceGetAttribute：一次查一项

只需要个别属性时，用 hipDeviceGetAttribute 写起来更直接，属性名也和 CUDA 一一对应、便于查表。（它并不更省时间：ROCm 的实现每次调用都会先构造一整份 hipDeviceProp_t 再取出一项。不过两种方式单次都不到 1 微秒，不必为性能去挑。）

// 原型：hipError_t hipDeviceGetAttribute(int* value, hipDeviceAttribute_t attr, int device);
int l2_bytes = 0, mem_khz = 0;
HIP_CHECK(hipDeviceGetAttribute(&l2_bytes, hipDeviceAttributeL2CacheSize, 0));
HIP_CHECK(hipDeviceGetAttribute(&mem_khz, hipDeviceAttributeMemoryClockRate, 0));

属性名全部以 hipDeviceAttribute 开头，定义在同一个头文件的 enum hipDeviceAttribute_t 里。查找某个属性名及其单位：

grep -n "hipDeviceAttribute" /opt/rocm/include/hip/hip_runtime_api.h | less

单位是最常见的坑：容量类属性单位是字节；频率类属性（如 hipDeviceAttributeClockRate）单位是 kHz，换成 MHz 要除以 1000。另一个坑是名字相近的属性：例如 hipDeviceAttributeMaxRegistersPerBlock（每个 block 可用的寄存器数，本机 131072）与 LDS 容量毫无关系。拿不准时，打开头文件看注释；注释没写单位时，用已知的值反推（例如 L2 查到 4194304，显然单位是字节）。

§5.3处理架构名字符串

hipDeviceProp_t::gcnArchName 是一个以 '\0' 结尾的字符数组，本机的值是 "gfx942:sramecc+:xnack-"。冒号前是架构代号，后面是“目标特性”：sramecc+ 表示片上存储开启了 ECC 校验，xnack- 表示关闭了 GPU 缺页重试。编译选项 --offload-arch=gfx942 只需要冒号前那部分。

从 C 字符串中截取“某个分隔符之前的部分”，思路是三步：

  1. 用 std::strchr(s, ':') 找到第一个冒号的位置（找不到时返回 nullptr，此时整个字符串都要）。
  2. 两个指针相减得到要复制的长度；再确保它不超过目标数组容量减 1（要给 '\0' 留位置）。
  3. 复制这么多个字符（std::memcpy 或 std::strncpy），然后手动在末尾写 '\0'。

std::strncpy(dst, src, len) 在 strlen(src) >= len 时（包括恰好相等）不会自动补 '\0'。只复制前缀时，结尾的 '\0' 必须自己写。

补全 query_device(device)：按结构体注释，用 §5.1–§5.3 的 API 把架构名、CU 数、wavefront 宽度、block 线程上限、LDS 容量、显存容量和核心频率填成本机实测值（TODO a2-1 至 a2-7）。不允许写死任何数字。

§6工具

§6.1rocm-smi：看谁在用卡

这台机器是多人共享的。跑任何东西之前，先看一眼各张卡的占用：

rocm-smi --showuse --showmemuse     # 每张卡的计算占用（GPU use %）和显存占用（VRAM %）
rocm-smi                            # 概览：温度、功耗、频率、占用

输出里的 GPU[0] … GPU[7] 就是 8 张卡。make grade 和 make verify 会自动挑“计算占用 + 显存占用”最小的那张卡，并在第一行打印出来。本机也装了更新的 amd-smi，例如 amd-smi static -g 7 可以看到第 7 张卡的缓存、显存等静态信息（§2.3 的表中有几项就来自它）。

§6.2HIP_VISIBLE_DEVICES：选卡

环境变量 HIP_VISIBLE_DEVICES 决定程序能“看见”哪些 GPU。被选中的卡会重新从 0 编号：

HIP_VISIBLE_DEVICES=7 ./build/run-a2     # 程序里只有一张卡，它就是 device 0（物理上的 7 号卡）
HIP_VISIBLE_DEVICES=6,7 ./some_program   # 程序里有两张卡：device 0 = 物理 6 号，device 1 = 物理 7 号

这就是为什么 a2 的测试总是查询 device 0：无论判分脚本选了哪张物理卡，在程序看来它都是 0 号。你手动运行 make run 时，也可以先用 rocm-smi 找一张空闲的卡，再在命令前加上 HIP_VISIBLE_DEVICES=…；如果你已经设置了这个变量，make grade 会尊重你的选择而不再自动挑卡。

§6.3rocprofv3：看 kernel 跑了多久

rocprofv3 是 ROCm 自带的性能分析工具（本机 /opt/rocm/bin/rocprofv3）。最基本的用法是 kernel 跟踪：记录程序启动的每一个 kernel 的名字、启动参数和起止时间。在 lab0-env/ 下先用 make run A=a1 编译出 build/run-a1，然后：

rocprofv3 --kernel-trace --stats --output-format csv -d prof -o a1 -- ./build/run-a1

-- 之后是要分析的程序及其参数。--output-format csv 不能省：ROCm 7 起 rocprofv3 默认只输出一个 rocpd 数据库文件（<主机名>/<进程号>_results.db），不加这个选项就找不到下面说的 CSV。运行时终端上会混有大量以 W/E/I 加日期开头的日志行，属于正常现象。结束后 prof/ 下会出现几个 CSV 文件，最有用的两个：

  • a1_kernel_stats.csv：按 kernel 名字汇总的调用次数、总耗时、平均耗时（纳秒）。
  • a1_kernel_trace.csv：每次启动一行，含 Kernel_Name、Start_Timestamp/End_Timestamp（纳秒）、Workgroup_Size_X、Grid_Size_X、VGPR_Count 等。

本机对 a1 参考实现实测的 a1_kernel_stats.csv 前几行：

"Name","Calls","TotalDurationNs","AverageNs",...
"__amd_rocclr_copyBuffer",18,56919,3162.166667,...
"__amd_rocclr_fillBufferAligned",8,47720,5965.000000,...
"fill_ids_kernel(int*, int)",5,31080,6216.000000,...

你自己的 kernel 出现在列表里；名字以 __amd_rocclr_ 开头的是 HIP 运行时内部的 kernel，由 hipMemset/hipMemcpy 这类调用产生。

trace 里的 Grid_Size_X 是线程总数（AMD/HSA 的约定），不是 block 个数。例如 grid = 4、block = 256 时它显示 1024。和 HIP 启动语法里的 grid 含义不同，读的时候别混淆。
