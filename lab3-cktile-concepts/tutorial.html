§1Layout = 坐标变换的组合

回忆 Lab 2 §3.1：tensor view = 一块内存（buffer view）+ 一个描述符（tensor descriptor）。那时描述符只是“长度 n、stride 1”，存在感很低。再回忆 Lab 1 a2：LDS 里的 tile[64][64 + 1] 多加的那一列 padding，让你在每一处读写 LDS 的地方都改了下标公式。布局一变、公式全改——这正是 Lab 2 §1.1 里的痛点 3。

CK-Tile 的做法是把“布局”做成一个对象：kernel 永远用逻辑坐标（第几行、第几列、第几块……）访问数据，描述符负责把逻辑坐标翻译成内存里的线性偏移。描述符本身由一串坐标变换拼成，每个变换只做一件小事（重排、合并、拆分、异或……）。换布局 = 换描述符，kernel 主体一行不改。这一节讲清楚这串变换怎么搭，a1 让你亲手搭五个。

§1.1上层、下层与 calculate_offset

先固定几个词。一个描述符可以看成一张自上而下的“翻译流水线”：

  • 上层维度（top / upper）：你拿来索引的逻辑坐标，例如矩阵的 (i, j)。get_num_of_top_dimension() 返回它有几维。
  • 下层维度（lower）：某个变换算出来、交给下一层的坐标。
  • hidden 维度：adaptor 把流水线里出现的每一个维度（最上层、中间层、最底层）统一编号，这个编号叫 hidden id，源码里大量的 hidden_ids 指的就是它。上层维度、底层维度各自是其中的一个子集（tensor_adaptor.hpp 的 get_top_dimension_hidden_ids() / get_bottom_dimension_hidden_ids() 返回的就是它们的编号）。
  • 最底层只有一维：线性偏移（以元素为单位，不是字节）。

每个坐标变换都知道“给我上层坐标，我算出下层坐标”——源码里统一叫 calculate_lower_index(idx_low, idx_up)。calculate_offset 就是把上层坐标从顶到底依次喂给每个变换，最后取最底层那一维：

template <typename Idx>
CK_TILE_HOST_DEVICE constexpr index_t calculate_offset(const Idx& idx) const
{
    return Base::calculate_bottom_index(idx)[number<0>{}];
}

Base 是 tensor_adaptor——一个“只做坐标翻译、不管内存”的对象。描述符 = adaptor + 元素空间大小（get_element_space_size()，§1.2）+ 最内维的“向量长度承诺”（模板参数 GuaranteedVectorLengths / GuaranteedVectorStrides，§1.2 末尾与 §3.4）。

描述符常用的几个成员函数（全部 constexpr，长度、stride 都用 number<…> 给出时可以在编译期求值，于是能用 static_assert 检查——本节的片段都这样做）：

§1.2naive descriptor 与 stride

最底下的那块“底座”由 make_naive_tensor_descriptor(长度, stride) 造出：两个 tuple，第 d 项分别是第 d 维的长度和 stride，偏移就是

offset = idx[0]·stride[0] + idx[1]·stride[1] + … // embed 变换

记住 stride 的含义只有一句话：stride[d] = 第 d 维坐标加 1 时，内存地址前进多少个元素。行主序（C 语言的二维数组）就是“最后一维 stride 为 1、前一维 stride 为一整行的长度”；列主序（Fortran / BLAS 的习惯）反过来，是第一维连续：沿行号走一步地址加 1，沿列号走一步跳过一整列。同一组长度配不同的 stride，就是同一个形状的不同内存布局。

// 三维张量 (2, 3, 4)，行主序：沿最后一维走一步地址 +1，沿中间一维 +4，沿第一维 +12
constexpr auto d3 = make_naive_tensor_descriptor(
    make_tuple(number<2>{}, number<3>{}, number<4>{}),     // 各维长度
    make_tuple(number<12>{}, number<4>{}, number<1>{}));   // 各维 stride
static_assert(d3.get_num_of_top_dimension() == 3);
static_assert(d3.calculate_offset(make_tuple(1, 2, 3)) == 1 * 12 + 2 * 4 + 3);   // = 23

// 4 × 6 的矩阵放在每行 8 个元素的缓冲区里（行间留 2 个空位）：只有行 stride 变了
constexpr auto padded = make_naive_tensor_descriptor(
    make_tuple(number<4>{}, number<6>{}),
    make_tuple(number<8>{}, number<1>{}));
static_assert(padded.calculate_offset(make_tuple(2, 5)) == 21);
static_assert(padded.get_element_space_size() == 30);    // (4-1)·8 + (6-1)·1 + 1，最后一行后面不算空位

§1.3pass_through 与维度重排

naive 描述符只能表达“偏移是坐标的线性组合”。更多的布局要靠在它上面叠变换，入口只有一个函数：

template <typename OldTensorDescriptor,
          typename NewTransforms,
          typename NewLowerDimensionOldTopIdss,
          typename NewUpperDimensionNewTopIdss>
CK_TILE_HOST_DEVICE constexpr auto
transform_tensor_descriptor(const OldTensorDescriptor& old_tensor_desc,
                            const NewTransforms& new_transforms,
                            NewLowerDimensionOldTopIdss,
                            NewUpperDimensionNewTopIdss)

模板参数的名字已经把四个参数的意思说全了：

  1. 旧描述符（底座）。新描述符的“下层”就是它的上层。
  2. 新变换列表：一个 tuple，每项是一个变换对象。
  3. 每个变换吃旧上层的哪些维度（NewLowerDimensionOldTopIds）：一个 tuple，第 k 项是一个 sequence，列出变换 k 的输入是旧描述符上层的第几维。
  4. 每个变换产出新上层的哪些维度（NewUpperDimensionNewTopIds）：形状同上，第 k 项列出变换 k 的输出在新描述符的上层排第几。

后两个参数只用类型（没有参数名），所以写成 make_tuple(sequence<…>{}, …) 这样的空对象。

最简单的变换是 pass_through：一维进、一维出，坐标原样传下去。它唯一的参数是这一维的长度（要和它吃掉的那一维一样长）：

template <typename LowIdx, typename UpIdx>
CK_TILE_HOST_DEVICE static constexpr void calculate_lower_index(LowIdx& idx_low,
                                                                const UpIdx& idx_up)
{
    static_assert(LowIdx::size() == 1 && UpIdx::size() == 1,
                  "wrong! inconsistent # of dimension");

    idx_low(number<0>{}) = idx_up[number<0>{}];
}

“原样传下去”怎么能改变布局？关键在第 3、4 个参数：变换 k 从旧的第 a 维拿坐标、却挂到新的第 b 维上。a ≠ b 时，维度就换了位置。下面把 §1.2 的三维张量 (a, b, c) 改成以 (c, a, b) 为上层坐标的视图：

// 底座：上一段的 d3，维度记作 (a, b, c)，长度 (2, 3, 4)
// 目标：新视图的上层坐标是 (c, a, b)，即把最后一维挪到最前面
// 写法：按“新上层的顺序”列出变换——变换 k 就产出新第 k 维，置换写在第 3 个参数里
constexpr auto cab = transform_tensor_descriptor(
    d3,                                                    // ① 底座（旧描述符）
    make_tuple(make_pass_through_transform(number<4>{}),   // ② 变换列表：变换 0 管 c（长度 4）
               make_pass_through_transform(number<2>{}),   //              变换 1 管 a（长度 2）
               make_pass_through_transform(number<3>{})),  //              变换 2 管 b（长度 3）
    make_tuple(sequence<2>{}, sequence<0>{}, sequence<1>{}),   // ③ 变换 k 吃旧上层的哪些维度：c、a、b
    make_tuple(sequence<0>{}, sequence<1>{}, sequence<2>{}));  // ④ 变换 k 产出新上层的哪些维度

static_assert(cab.get_length(number<0>{}) == 4);           // 新的第 0 维是 c，长度 4
static_assert(cab.calculate_offset(make_tuple(3, 1, 2)) == 1 * 12 + 2 * 4 + 3);   // (c,a,b)=(3,1,2)

同一个置换还有另一种写法：按旧维度的顺序列出变换（长度依次 2、3、4），第 3 个参数写成 0、1、2，把置换放进第 4 个参数。两种写法得到的描述符完全相同，但要注意第 3 个参数记的是“从哪来”、第 4 个参数记的是“到哪去”，同一个置换在两处写出来的数字一般不一样。自己练一下：把 cab 改成第二种写法，第 4 个参数应该是什么？写出来后用 static_assert 核对 (3, 1, 2) 的偏移。

读这类代码的口诀：按列表下标 k 竖着读三样东西——变换 k、它吃的旧维度、它产出的新维度。新描述符每一维的长度也由变换给出（pass_through 的长度就是它的参数），所以上面 cab.get_length(number<0>{}) 是 4。

  • 第 4 个参数的编号跳号（例如产出 0、1、3）：编译失败，static assertion failed … is_valid_sequence_map<… sequence<0, 1, 3>> … wrong! invalid reorder map。新上层的编号必须恰好是 0 … n−1，各出现一次。
  • 变换个数与两个 sequence 列表的项数不一致：编译失败，wrong! inconsitent number of transform（源码原文的拼写）。
  • 漏吃了旧上层的某一维（例如对三维的 d3 只写两个 pass_through，吃第 0、1 维）：能编译、能运行，漏掉的那一维被当成恒为 0。实测 calculate_offset(make_tuple(1, 2)) 得到 1·12 + 2·4 = 20，静默地少了一维。写完变换后，数一数第 3 个参数里是否每个旧维度都出现了。

对应 a1 的 a1-2（转置视图）。

§1.4merge：多个维度合成一个

merge 吃多个下层维度、产出一个上层维度。参数是被合并各维的长度，先列出的是高位——就像把 (时, 分, 秒) 合成“当天第几秒”。求偏移时方向相反：拿到上层的一个数 k，用除法和取模拆回各维坐标：

CK_TILE_HOST_DEVICE constexpr void calculate_lower_index(LowIdx& idx_low,
                                                         const UpIdx& idx_up) const
{
    static_assert(LowIdx::size() == NDimLow && UpIdx::size() == 1,
                  "wrong! inconsistent # of dimension");

    index_t tmp = idx_up[number<0>{}];

    // division and mod
    static_for<0, NDimLow - 1, 1>{}([&](auto i) {
        idx_low(i) = tmp / this->low_lengths_scan_[i];
        tmp %= this->low_lengths_scan_[i];
    });

    idx_low(number<NDimLow - 1>{}) = tmp;
}

low_lengths_scan_[i] 是第 i 维之后所有长度之积（“反向排他前缀积”）。例如长度 (3, 4)：scan = (4, 1)，k = 7 → (7 / 4, 7 % 4) = (1, 3)。我们调用的 make_merge_transform（第 1614–1618 行）默认返回另一个实现 merge_v2_magic_division，结果完全相同，只是用“乘一个魔数再移位”代替了整数除法——GPU 上整数除法很贵。

// (a, b, c) → (k, b)：把不相邻的 a、c 两维合成一维 k，b 原样留下
// a 当高位、c 当低位：k = a·4 + c
constexpr auto k_b = transform_tensor_descriptor(
    d3,
    make_tuple(make_merge_transform(make_tuple(number<2>{}, number<4>{})),   // 长度按“高位在前”：(a, c)
               make_pass_through_transform(number<3>{})),
    make_tuple(sequence<0, 2>{}, sequence<1>{}),     // merge 吃旧的第 0、2 维；b 是旧的第 1 维
    make_tuple(sequence<0>{}, sequence<1>{}));       // merge 只产出新的第 0 维，b 去新的第 1 维
static_assert(k_b.get_num_of_top_dimension() == 2);
static_assert(k_b.get_length(number<0>{}) == 8);
static_assert(k_b.calculate_offset(make_tuple(5, 1)) == 17);   // k=5 → (a,c)=(1,1) → 12+4+1

// 同样两维，换个顺序合并：c 当高位、a 当低位，k = c·2 + a
constexpr auto k_b2 = transform_tensor_descriptor(
    d3,
    make_tuple(make_merge_transform(make_tuple(number<4>{}, number<2>{})),
               make_pass_through_transform(number<3>{})),
    make_tuple(sequence<2, 0>{}, sequence<1>{}),     // 先列出的（c）是高位
    make_tuple(sequence<0>{}, sequence<1>{}));
static_assert(k_b2.calculate_offset(make_tuple(1, 0)) == 12);   // k=1 → (c,a)=(0,1) → 12

§1.5unmerge 与分块视图

unmerge 是 merge 的反方向：吃一个下层维度、产出多个上层维度。参数是拆出来的各段长度，同样先写高位。求偏移时它把上层的几个坐标合回一个数：

template <typename LowIdx, typename UpIdx>
CK_TILE_HOST_DEVICE constexpr void calculate_lower_index(LowIdx& idx_low,
                                                         const UpIdx& idx_up) const
{
    if constexpr(!Use24BitIntegerCalculation)
    {
        idx_low(number<0>{}) = idx_up[number<NDimUp - 1>{}];

        static_for<0, NDimUp - 1, 1>{}(
            [&](auto i) { idx_low(number<0>{}) += idx_up[i] * up_lengths_scan_[i]; });
    }

最后一个上层坐标直接加，其余乘以“它之后各段长度之积”再加。只有乘加，没有除法，所以 unmerge 比 merge 便宜得多。

分块（tiling）就是 unmerge 的典型用途。Lab 1 a4 的分块 GEMM 里，一个元素的行号可以写成“第几块 × 块高 + 块内第几行”——这正是把行这一维 unmerge 成 (块号, 块内坐标) 两维。下面的例子只拆列：4 × 8 的矩阵，把每行 8 列拆成 2 组 × 每组 4 个（j = g·4 + k），并且故意把新上层的顺序定成 (k, i, g)，好把“编号”这件事看清楚：

// 4 × 8 行主序，把每行的 8 列拆成 2 组 × 每组 4 个：列 j = g·4 + k
// 新上层的顺序定为 (k, i, g)——组内位置 k 放在最前面，组号 g 放在最后
constexpr auto rm48 = make_naive_tensor_descriptor(make_tuple(number<4>{}, number<8>{}),
                                                   make_tuple(number<8>{}, number<1>{}));
constexpr auto kig = transform_tensor_descriptor(
    rm48,
    make_tuple(make_pass_through_transform(number<4>{}),                        // 行 i 原样
               make_unmerge_transform(make_tuple(number<2>{}, number<4>{}))),   // 列 j → (g, k)，g 是高位
    make_tuple(sequence<0>{}, sequence<1>{}),        // 两个变换各吃一个旧维度
    make_tuple(sequence<1>{}, sequence<2, 0>{}));    // i 去新第 1 维；unmerge 的两个输出 (g, k) 依次去新第 2、0 维
static_assert(kig.get_num_of_top_dimension() == 3);
static_assert(kig.get_length(number<0>{}) == 4 && kig.get_length(number<2>{}) == 2);
static_assert(kig.calculate_offset(make_tuple(3, 2, 1)) == 2 * 8 + 1 * 4 + 3);   // (k,i,g)=(3,2,1)

注意第 4 个参数里 unmerge 那一项 sequence<2, 0>，两条规则都在这里：

  • sequence 里的第 m 项，对应这个变换的第 m 个输出——unmerge 的输出顺序就是它长度列表的顺序 (g, k)。所以 2 是 g 的去处、0 是 k 的去处，而不是反过来。
  • 一个变换产出的几维不必相邻、也不必递增：k 去了新的第 0 维、g 去了新的第 2 维，中间的第 1 维留给 pass_through 产出的行号 i。来自不同变换的维度可以任意交错。

§1.6xor swizzle 与 LDS bank

回到 LDS。Lab 1 §3.6 的结论：LDS 有 32 个 bank，对 float 数组，bank = 偏移 mod 32；半个 wavefront（32 个 lane）里若有 k 个 lane 访问同一个 bank 的不同地址，就要串行 k 次。32 × 32 的行主序 tile 按列读（第 i 个 lane 读 (i, j)），偏移 i·32 + j 的 bank 都是 j，32 路冲突。padding（行间距 33）把 bank 错开成 (i + j) mod 32，但有两个代价：多占内存；而且每行的起点 i·33 不再是 4 的倍数——行首不再 16 字节对齐，一次读写 4 个 float 的向量访问失去了对齐保证（§2.4 末尾有本机实测）。

xor swizzle 不加空位，而是在每一行内部把列打乱：逻辑上的第 j 列，存到这一行的第 j ^ (i mod N) 个位置（^ 是按位异或）。对固定的 i，j ↦ j ^ i 是 0…N−1 上的一个置换（N 是 2 的幂时），所以每行的数据仍然恰好占满这一行，行首对齐不变；而按列读时，固定 j、i 从 0 走到 31，物理位置 j ^ i 两两不同，32 个 lane 落在 32 个不同的 bank 上——没有冲突，也没有浪费。

CK-Tile 里它就是 xor_t 变换：两维进、两维出。

template <typename LowIdx, typename UpIdx>
CK_TILE_HOST_DEVICE constexpr void calculate_lower_index(LowIdx& idx_low,
                                                         const UpIdx& idx_up) const
{
    static_assert(LowIdx::size() == 2 && UpIdx::size() == 2,
                  "wrong! inconsistent # of dimension");

    idx_low(number<0>{}) = idx_up[number<0>{}];

    idx_low(number<1>{}) =
        idx_up[number<1>{}] ^ (idx_up[number<0>{}] % up_lengths_[number<1>{}]);
}

逐项读：下层第 0 维 = 上层第 0 维（原样）；下层第 1 维 = 上层第 1 维 异或（上层第 0 维 mod 第 1 维的长度）。make_xor_transform(make_tuple(长度0, 长度1)) 构造它（第 1661–1665 行），up_lengths_ 就是你传入的这两个长度。注意被修改的永远是第二个分量，用来“打乱它”的是第一个分量——所以把哪个旧维度排成 xor 的第 0 个分量、哪个排成第 1 个分量（第 3 个参数里 xor 那一项的顺序），决定了“哪一维被打乱”；第 4 个参数则决定这两个分量在新上层排第几（下面的例子会把它们换个位置）。

真实的 kernel 往往一次读 4 个连续 float（16 字节），这时要保证 swizzle 不把这 4 个拆散：只在“4 个一组”的粒度上打乱组号，组内保持连续。下面把每行 16 个 float 看成 4 组 × 4 个，即形状 (i, g, v) = (8, 4, 4)，只对 (i, g) 做 xor；同时让新视图的上层按 (g, i, v) 排列，看清楚“xor 内部谁打乱谁”和“输出挂到新上层第几维”是两件独立的事：

// 8 行 × 16 个 float，每 4 个 float 一组（一次 16 字节向量访问），即底座形状 (i, g, v) = (8, 4, 4)
constexpr auto base3 = make_naive_tensor_descriptor(
    make_tuple(number<8>{}, number<4>{}, number<4>{}),
    make_tuple(number<16>{}, number<4>{}, number<1>{}));
// 只在“组”的粒度上做 swizzle：组号 g 换成 g ^ (i % 4)，组内的 4 个元素保持连续。
// 新视图的上层坐标按 (g, i, v) 排列——先组号、再行号
constexpr auto swizzled = transform_tensor_descriptor(
    base3,
    make_tuple(make_xor_transform(make_tuple(number<8>{}, number<4>{})),   // xor 的两个分量：(i, g)，g 被打乱
               make_pass_through_transform(number<4>{})),                   // v 原样
    make_tuple(sequence<0, 1>{}, sequence<2>{}),    // xor 吃旧的 (i, g)
    make_tuple(sequence<1, 0>{}, sequence<2>{}));   // xor 的输出 (i, g) 依次去新第 1、0 维
static_assert(swizzled.get_length(number<0>{}) == 4);   // 新第 0 维是 g
static_assert(swizzled.calculate_offset(make_tuple(2, 5, 3)) == 5 * 16 + (2 ^ (5 % 4)) * 4 + 3);   // (g,i,v)=(2,5,3)，= 95

§2.1二维 encoding 的读法

二维 tile 有两个 X 维：X0 是行、X1 是列。tile_distribution_encoding 的六个参数和 Lab 2 §3.2 完全一样，只是 H 现在有两个 sequence（每个 X 维一个），(major, minor) 地址里 major = 1 指 X0、major = 2 指 X1（major = 0 仍然是 R）。下面是本节的贯穿例子：2 个 wavefront（128 线程）读一个 32 × 32 的 tile，每个线程每次读同一行里连续的 4 个 float。

// 2 个 wavefront（128 线程）读一个 32 × 32 的 tile
//   行 X0 = 32 = 2 (warp) × 8 (lane 的高位) × 2 (Y0)
//   列 X1 = 32 = 8 (lane 的低位) × 4 (Y1，连续 4 个 float)
using Enc32x32 = tile_distribution_encoding<
    sequence<>,                                  // R：不复制
    tuple<sequence<2, 8, 2>, sequence<8, 4>>,    // H：X0 的三段，X1 的两段
    tuple<sequence<1>, sequence<1, 2>>,          // P0 (warp) → X0；P1 (lane) → X0 和 X1 …
    tuple<sequence<0>, sequence<1, 0>>,          //   … 第 0 段；    … X0 第 1 段、X1 第 0 段
    sequence<1, 2>,                              // Y0 → X0，Y1 → X1 …
    sequence<2, 1>>;                             //   … X0 第 2 段，X1 第 1 段

读 encoding 最稳的办法是先把它还原成一张表：每一行是一个 H 段，写出它属于哪个 X、长度多少、被谁认领。

把 Lab 2 §3.2 的自查清单推广到二维，设计一个 encoding 时逐条核对：

  1. 每个 X 维：H 各段之积 = tile 在这一维的长度（例子：2·8·2 = 32，8·4 = 32）。
  2. H 的每一段恰好被一个 P 或一个 Y 认领，不重不漏。
  3. P0（warp）认领的段长之积 = block 里的 wavefront 数（2）；P1（lane）认领的段长之积 = 64（8·8，即 get_warp_size()，Lab 2 §3.2）。
  4. 线程总数 × 每线程元素数（∏Y = 2·4）= tile 元素数（128·8 = 1024）。
  5. 让一个 Y 认领 X1 的最后一段，它在内存里连续，才能向量化；惯例上放在 Y 的最后。

§2.2一个 P 映射到多个 H 段

上面的 P1 同时认领了行方向的一段和列方向的一段，于是一个 wavefront 的 64 个 lane 排成了“8 行 × 8 个列组”的小方阵——这就是“lane 同时覆盖行和列”。它的写法是在 P→major / P→minor 里给这个 P 维写多项：sequence<1, 2> / sequence<1, 0> 读作“先 X0 的第 1 段、再 X1 的第 0 段”。规则只有一条：先列出的段是 lane id 的高位。如果把两项顺序反过来写（先 X1 的段、再 X0 的段），lane id 的低位就跑到行方向：lane 0、1、2… 依次往下走，相邻 lane 读的是不同行。

为什么要让 lane 跨两个方向？一行只有 32 个 float，8 个 lane × 4 个就读完了；剩下的 lane 只能去别的行。设计时要同时照顾两件事：

  • 相邻 lane 读相邻地址：同一行的 8 个 lane 首尾相接，一共 128 字节连续，这是合并访存（Lab 1 §3.1）的前提。
  • Y 段摆在哪里，决定一条指令覆盖哪些行。例子里 Y0 是行方向的最低段，同一个线程拿相邻两行；于是 y0 = 0 的那条指令里，wavefront 0 读的是第 0、2、4…14 行。若把 Y0 挪到行方向的最高段（X0 = Y0 2 × warp 2 × lane 8），实测线程 0 拿第 0 行和第 16 行，y0 = 0 的那条指令里 wavefront 0 读的是第 0–7 行——连续的 1 KiB。两种都正确、都合并，只是“每条指令碰到的地址”不同；用下面的小部件对比这两个预设。

下面的小部件可以编辑任意二维 encoding：给 X0、X1（以及 R）各列出若干段，每段选长度和认领者。它按 CK-Tile 的规则算出每个元素属于哪个 (warp, lane, Y)，并自动核对上面的清单。预设中的映射已与本机 GPU 上 load_tile 的实测结果逐元素比对过。

CK-Tile 不检查这一条。lane 认领的段之积小于 64 时，多出来的 lane 算出的坐标落在 tile 之外；大于 64 时，有一部分元素永远没有 lane 去拿（lane id 最大只有 63）。两种情况都能编译、能运行，只是静默出错——和 Lab 2 “1 个 P 维用在多 wavefront 上”是同一类坑。在小部件里把某个 lane 段的长度改一下就能看到。

§2.3pad_tensor_view 与二维边界

Lab 2 §3.1 讲过，naive 视图的越界保护只有一层：buffer 指令的硬件 range = 视图的元素空间大小（§1.2 的 get_element_space_size()），软件层的 is_valid 标志对 naive 视图恒为 true。一维时这就够了：越过末尾的访问一定越过 range。二维就不一样了——列越界不等于线性偏移越界。rows × cols 的行主序矩阵里，(r, c) 的偏移是 r·cols + c；c ≥ cols 时这个数照样可能小于 rows·cols，于是访问落到了下一行的开头。

带行间距 ld（ld > cols）时情况类似：range 是 §1.2 的元素空间大小 (rows − 1)·ld + cols，而不是 rows·cols；列方向小幅越界落在行间空位里，越界超过 ld − cols 才碰到下一行的数据，只有伸出最后一行末尾的部分才会被硬件屏蔽。这正是 Lab 2 §4.1 第 1 问所说的“漏网”。读完本节的 pad 视图（它让 is_valid 标志真正起作用）后，也可以回头做 Lab 2 §4.3 第 2 问（oob_conditional_check 为 false 时省掉了什么）。

§2.4LDS 视图：padding 与“同一块内存的两个视图”

LDS 上同样用 make_naive_tensor_view，只是地址空间换成 address_space_enum::lds，指针指向 __shared__ 数组。tile 的大小在编译期就确定，所以 LDS 视图的长度和 stride 通常都写成 number<…>；视图的形状一般就是 tile 本身，窗口原点是 {0, 0}。

padding 就是 §1.2 的行间距：逻辑上 R × C，行 stride 写成 C + 1，__shared__ 数组也按 R × (C + 1) 声明。它的作用与 Lab 1 §3.6 完全相同——在小部件 1.1 里选“行主序 + padding”，按列高亮，看 bank 如何被错开。

同一块内存的多个视图。视图 = 指针 + 描述符。指针相同、描述符不同，就是同一块内存的不同“看法”——这正是 a1 里转置视图、分块视图的意义，只是现在内存是 LDS。下面的例子给同一块 8 × 6（行间距 7）的 LDS 挂了两个视图：A 是完整的矩阵；B 只看偶数行，形状 4 × 6，行 stride 翻倍。

__global__ void two_views(float* out) {
  constexpr index_t R = 8, C = 6, LD = C + 1;          // 每行多留 1 个 float
  __shared__ float smem[R * LD];
  // 视图 A：完整的 8×6 矩阵
  auto va = make_naive_tensor_view<address_space_enum::lds>(
      smem, make_tuple(number<R>{}, number<C>{}), make_tuple(number<LD>{}, number<1>{}), number<1>{}, number<1>{});
  // 视图 B：同一块内存，只看偶数行——形状 4×6，行 stride 翻倍
  auto vb = make_naive_tensor_view<address_space_enum::lds>(
      smem, make_tuple(number<R / 2>{}, number<C>{}), make_tuple(number<2 * LD>{}, number<1>{}), number<1>{}, number<1>{});
  (void)va; (void)vb;
}

§2.5block_sync_lds 与完整数据流

LDS 是 block 内所有 wavefront 共享的。一个 wavefront 写、另一个 wavefront 读之前，必须保证写已经完成——这就是 Lab 1 里的 __syncthreads()（Lab 1 §3.5）。CK-Tile 对应的函数是 block_sync_lds()：

template <index_t lgkmcnt = 0>
CK_TILE_DEVICE void block_sync_lds()
{
    s_waitcnt_barrier<waitcnt_arg::kMaxVmCnt, waitcnt_arg::kMaxExpCnt, lgkmcnt>();
}

往上看第 257–279 行：在 gfx942 上它展开成 s_waitcnt lgkmcnt(0)（等本 wavefront 发出的 LDS 读写全部完成）再加 s_barrier（等 block 内所有 wavefront 都到达）；全局内存的计数器 vmcnt 取最大值，即“不等”。本机对比过：同一段“写 LDS → 同步 → 读 LDS”的代码，用 __syncthreads() 和用 block_sync_lds() 编译出的指令完全相同。CK-Tile 自己封装一层，是为了在流水线化的 kernel 里精确控制“等哪个计数器、等到几”（模板参数 lgkmcnt；同文件第 287–291 行还有只等 vmcnt 的 block_sync_lds_direct_load：在 gfx942 上 vmcnt 同时计数向量内存的读和写，典型用途是“buffer_load 直接写入 LDS”之后的同步），本课用默认值即可。

把前面的东西串起来，一个经过 LDS 的 kernel 有固定的五步。下面的例子是一个“看起来什么都没做”的拷贝 out = in（形状 rows × 32），但它在 LDS 里换了一次分布：用 §2.1 的 Enc32x32（适合合并读全局内存）读进来、写进 LDS；同步；再用另一个分布——每个线程拿同一列里连续 8 行——从 LDS 读出来，写回全局内存。

constexpr index_t kT = 32, kLd = kT + 1;   // 32×32 的 tile；LDS 每行多留 1 个 float

// 分布 A（§2.1 的 Enc32x32）：同一行的 8 个 lane 各取 4 个连续 float，适合读写全局内存
// 分布 B：每个线程拿同一列里连续的 8 行
using EncColumn = tile_distribution_encoding<
    sequence<>,
    tuple<sequence<2, 2, 8>, sequence<32>>,      // X0 = warp 2 × lane 高位 2 × Y 8；X1 = lane 低位 32
    tuple<sequence<1>, sequence<1, 2>>,
    tuple<sequence<0>, sequence<1, 0>>,
    sequence<1>,
    sequence<2>>;

// out = in（形状 n_tiles·32 × 32），但中途经过 LDS 换了一次“谁拿哪个元素”
__global__ void redistribute(const float* in, float* out, index_t rows) {
  __shared__ float smem[kT * kLd];
  constexpr auto dist_a = make_static_tile_distribution(Enc32x32{});
  constexpr auto dist_b = make_static_tile_distribution(EncColumn{});
  const index_t row0 = static_cast<index_t>(blockIdx.x) * kT;

  auto vin = make_naive_tensor_view<address_space_enum::global>(
      in, make_tuple(rows, kT), make_tuple(kT, 1), number<4>{}, number<1>{});
  auto vout = make_naive_tensor_view<address_space_enum::global>(
      out, make_tuple(rows, kT), make_tuple(kT, 1), number<4>{}, number<1>{});
  auto vlds = make_naive_tensor_view<address_space_enum::lds>(
      smem, make_tuple(number<kT>{}, number<kT>{}), make_tuple(number<kLd>{}, number<1>{}),
      number<1>{}, number<1>{});

  auto win  = make_tile_window(vin,  make_tuple(number<kT>{}, number<kT>{}), {row0, 0}, dist_a);
  auto lw   = make_tile_window(vlds, make_tuple(number<kT>{}, number<kT>{}), {0, 0}, dist_a);
  auto lr   = make_tile_window(vlds, make_tuple(number<kT>{}, number<kT>{}), {0, 0}, dist_b);
  auto wout = make_tile_window(vout, make_tuple(number<kT>{}, number<kT>{}), {row0, 0}, dist_b);

  auto ta = load_tile(win);   // ① 全局 → 寄存器（分布 A）
  store_tile(lw, ta);         // ② 寄存器 → LDS
  block_sync_lds();           // ③ 等 block 里所有 wavefront 都写完
  auto tb = load_tile(lr);    // ④ LDS → 寄存器（分布 B）
  store_tile(wout, tb);       // ⑤ 寄存器 → 全局
}

§3在 tile 上归约

Lab 1 a3 的 shuffle 归约分三层：每个线程先在自己的寄存器里累加；再用 __shfl_down 在 wavefront 内两两合并（Lab 1 §4.3）；最后经 LDS 合并各个 wavefront（Lab 1 §4.4）。CK-Tile 的 tile 归约对应前两层，而且“哪些元素在线程内合并、哪些要跨 lane 合并”不用你决定——它们由分布推导出来：被归约的方向上，Y 认领的段在线程内合并，lane 认领的段跨 lane 合并。第三层（跨 wavefront）CK-Tile 的这组函数不做，见 §3.2 末尾。

本节的例子都在 ck_tile/ops/reduce/block/block_reduce.hpp 里，需要额外 #include "ck_tile/ops/reduce/block/block_reduce.hpp"。贯穿例子：1 个 wavefront 处理 8 行 × 64 列，求每行的最大值。

§3.1block_tile_reduce 与归约后的分布

先给例子的 tile 一个分布：行 X0 = Y0 2 × lane 高位 4，列 X1 = Y1 4 × lane 低位 16。注意列方向 Y1 在高段、lane 在低段：16 个相邻 lane 读一行里相邻的 16 列（合并访存），每个线程的 4 个元素彼此相隔 16 列。这样排是为了让下面的推导和图都简单；它的代价是每个线程的元素不连续，load 不能向量化（§2.1 清单第 5 条）。对 a3 来说，列方向怎么排、block 有几个 wavefront、tile 多大，要你自己按 §3.1–§3.4 的约束重新设计。

// 1 个 wavefront，8 × 64 的 tile
//   行 X0 = 8  = 2 (Y0) × 4 (lane 高位)
//   列 X1 = 64 = 4 (Y1) × 16 (lane 低位)——Y1 在高段，每个线程的 4 个元素相隔 16 列
using Enc8x64 = tile_distribution_encoding<
    sequence<>,
    tuple<sequence<2, 4>, sequence<4, 16>>,
    tuple<sequence<1, 2>>,          // 只有 1 个 P（lane）：认领 X0 第 1 段、X1 第 1 段
    tuple<sequence<1, 1>>,
    sequence<1, 2>,                 // Y0 → X0 第 0 段；Y1 → X1 第 0 段
    sequence<0, 0>>;

// 沿 X1（第 1 个 X 维，列方向）归约之后的分布——由 CK-Tile 推导，这里用 static_assert 核对
using Enc8x64Reduced = tile_distribution_encoding<
    sequence<16>,                   // R：原来 lane 在列方向的 16 段，变成了“复制”
    tuple<sequence<2, 4>>,          // 只剩 X0
    tuple<sequence<1, 0>>,          // lane 仍然认领两段：X0 第 1 段、R 第 0 段
    tuple<sequence<1, 0>>,
    sequence<1>,                    // Y0 保留；Y1 消失（已在线程内归约）
    sequence<0>>;
static_assert(std::is_same_v<
    decltype(detail::make_reduce_tile_distribution_encoding(Enc8x64{}, sequence<1>{})),
    Enc8x64Reduced>);

第一个函数 block_tile_reduce 只做线程内的那一层：

template <typename AccDataType_,
          typename InDistributedTensor_,
          index_t... InReduceDims,

CK_TILE_DEVICE auto block_tile_reduce(const InDistributedTensor_& in_tensor,

  • AccDataType_：累加器的类型，要显式写在尖括号里，例如 block_tile_reduce<float>(…)。
  • in_reduce_dims：要归约掉的 X 维编号。对行方向的结果（每行一个数）要消掉的是列，即 sequence<1>{}。注意当前实现只支持二维 tile、归约第 1 维：真正做线程内合并的那个重载把“外层遍历 X0、内层遍历 X1”写死了（第 186 行、第 237–249 行的 FIXME），而归约后的分布却按你写的维度推导。写 sequence<0>{} 也能编译、能运行，结果静默出错（本机实测：8 × 64 的 tile 按列求和，得到的数与正确值毫无关系，没有任何报错）。
  • reduce_func：二元函数 (a, b) → a ⊕ b；reduce_init：单位元（求和是 0，求最大值是 −∞），类型必须与输入元素类型相同（第 274 行的 static_assert）。

返回一个新的 distributed tensor：它的分布由 make_reduce_tile_distribution_encoding 从输入分布推导（第 277–280 行），然后对每个线程把被归约方向上的 Y 全部合并进去。

归约后的分布怎么推导？看 tile_distribution_encoding.hpp 第 562–758 行的 make_reduce_tile_distribution_encoding_impl，规则可以浓缩成三条：

  1. 被归约的 X 维从 H 中消失。
  2. 它原来由 Y 认领的段：线程内已经合并，对应的 Y 维消失。
  3. 它原来由 P 认领的段：变成一个新的 R（复制）段，P 改为认领这个 R 段——意思是“沿这一段排开的那些线程，最终应该持有同一个值”。

上面片段末尾的 static_assert 就是把推导结果和手写的 Enc8x64Reduced 逐字比较（本机编译通过）：列方向的 lane 低位 16 段变成了 R = (16)，Y1 消失，只剩 Y0。于是每个线程手里只剩 ∏Y = 2 个累加值（它负责的两行各一个），而同一行被 16 个 lane 分着算，每人只看了 4 列。

源码注释里的限制要当真：至少要留一个 Y 维不被归约。本机实测，用 Lab 2 那种“行方向只有 lane、没有 Y”的 4 × 64 分布去归约列，编译直接失败（tile_distribution_encoding.hpp:87 处 no matching constructor for initialization of 'array<index_t, NDimY>' 等一串错误）——归约后 Y 维个数为 0，后面的代码处理不了。所以设计分布时，结果方向（这里是行）上要有一个 Y 段，哪怕长度只是 1。

block_tile_reduce 有两个重载，参数个数都是 4，靠第一个参数区分。上面这个（第 261–269 行）返回一个新累加器：(in, dims, f, init)。同一个文件第 186–194 行的另一个以 已有的累加器为第一个参数：(acc, in, dims, f)，它不新建累加器、也没有 init，而是把 in 归约进 acc，acc 原地被修改、函数返回 void。“返回新累加器”的版本内部就是先建 acc、填上 init、再调它（第 276–291 行）。所以传进去的 acc，分布必须正好是 in 的分布归约之后的样子，而且已经有了合适的初值。当一行太长、要分几次 load 时，就用第二个重载把每一块累加到同一个 acc 上（§3.3）。

§2.3 的 pad_tensor_view 让越界位置读成 0。求和时 0 正好是单位元，不影响结果；求最大值就不是了。本机实测：8 × 60 的矩阵全是 −3，用 8 × 64 的窗口加 pad 求行最大值，结果是 0 而不是 −3——多出来的 4 列贡献了 0。本节例子刻意让列数恰好是 64，回避了这个问题。

§3.2block_tile_reduce_sync 与 lane 间 shuffle

第二个函数把 R 段上的部分结果合起来。它遍历累加器里的每个值，对每个“由 lane 认领的 R 段”做一轮 shuffle 归约：

static_for<0, NDimR, 1>{}([&](auto idim_r) {
    // FIXME: nasty to use does_p_own_r_
    if constexpr(DstrEncodeDetail::does_p_own_r_[idim_p_lane][idim_r])
    {
        constexpr index_t r_length = DstrEncode::rs_lengths_[idim_r];

        constexpr index_t lid_over_rid_derivative =
            DstrEncodeDetail::ps_over_rs_derivative_[idim_p_lane][idim_r];

        static_assert(is_power_of_two_integer(r_length),
                      "wrong! only support power of 2 reduction");

        constexpr index_t nstage = integer_log2_floor(r_length);

        // reduction sweep forward
        static_for<0, nstage, 1>{}([&](auto istage) {
            if constexpr(CrossWarp)
            {
                constexpr index_t lid_delta =
                    lid_over_rid_derivative * (1 << (nstage - istage - 1));

                // pull data from remote lane
                const auto v_remote = warp_shuffle_down(v_local, lid_delta);

                // reduce
                v_local = reduce_func(v_local, v_remote);
            }

逐行读：只处理“lane（idim_p_lane，即最后一个 P）拥有的 R 段”；R 段长度必须是 2 的幂；lid_over_rid_derivative 是“R 坐标加 1 时 lane id 加几”——例子里 R 段是 lane id 最低的那一段（长度 16，即 lane id 的低 4 位），所以是 1；然后做 log₂(16) = 4 轮，每轮从 lane + delta 拉一个值过来合并，delta 依次是 8、4、2、1。这和你在 Lab 1 a3 写的 wave_reduce 是同一个树形结构（那里的 delta 从 warpSize 推出、覆盖整个 64 lane 的 wavefront），只是这里的 delta 由分布在编译期决定、而且只在 16 个 lane 的范围内做。warp_shuffle_down（core/arch/utility.hpp 第 47–60 行）用的也正是 __shfl_down 背后的那条 ds_bpermute_b32，只是越界时行为不同：HIP 的 __shfl_down 在 lane + delta 超出 wavefront 时返回自己的值（hip/amd_detail/amd_warp_functions.h 第 375–381 行），CK 的版本直接把地址交给 ds_bpermute，按 64 回绕。本例中这些回绕来的值不会被用到（只有每组第一个 lane 的结果被保留），所以不影响结果。

树形归约之后，只有每组的第一个 lane 持有完整结果。默认参数 WithBroadcast = true 时，函数接着做第二遍（第 85–121 行）：用 warp_shuffle_up 把结果反向“广播”回同组的其他 lane，于是 16 个 lane 最终持有同一个值——正好满足 R 的含义。

同一个文件第 132 行起还有一个 block_tile_reduce_xor_sync：每轮让 lane 与 lane ^ (derivative << istage) 交换（第 170–171 行；istage 从 0 递增，伙伴依次是 lane^1、^2、^4、^8），这是“蝶形”归约，做完 log₂ 轮所有 lane 都已经是完整结果，不需要广播。本机对比用本节片段搭成的测试 kernel（每个线程 2 个累加值）的汇编：默认的 sync 每个累加值用 8 条 ds_bpermute_b32（4 轮归约 + 4 轮广播），共 16 条；xor 版本 8 条，结果相同。

本机实测（把三个片段放进一个每 block 1 个 wavefront、8 行的 kernel）：rows = 8、24、4096（输入大部分是负数，检验 −∞ 初值）逐位正确。再看中间过程：输入全设成 1、改成求和，打印每个 lane 的两个累加值——sync 之前每个 lane 都是 (4, 4)（自己那 4 列），sync 之后 64 个 lane 全都是 (64, 64)。

文件第 9 行的注释写得很直接：// This file is not support cross warp reduce。sync 只处理 lane 认领的 R 段，warp 认领的段即使被归约，也不会被合并（第 4 个模板参数虽然叫 CrossWarp，两个分支都只在 wavefront 内部换数据）。本机实测：2 个 wavefront、让 warp 认领列方向的一段（每行 128 列，每个 wavefront 管 64 列），全 1 输入，sync 之后两个 wavefront 各自得到 64，而不是 128——没有报错，只是结果错。要跨 wavefront 合并，得像 Lab 1 §4.4 那样经过 LDS 自己写。最简单的做法是设计分布时就让一行只落在一个 wavefront 里。

§3.3move_tile_window

到目前为止，一个窗口只 load 一次。行很长（或 GEMM 的 K 很大）时，一个 block 要沿着某个方向一块一块地走——窗口要能移动：

template <typename TensorView_,
          typename WindowLengths_,
          typename StaticTileDistribution_,
          index_t NumCoord>
CK_TILE_DEVICE void move_tile_window(
    tile_window_with_static_distribution<TensorView_,
                                         WindowLengths_,
                                         StaticTileDistribution_,
                                         NumCoord>& window,
    const typename tile_window_with_static_distribution<TensorView_,
                                                        WindowLengths_,
                                                        StaticTileDistribution_,
                                                        NumCoord>::BottomTensorIndex& step)
{
    window.move(step);
}

step 是一个 multi_index（和窗口原点同一个类型），按视图的维度给出“每一维挪多少”，通常写成花括号 {0, kTN}。窗口以非 const 引用传入、原地修改；它内部缓存的每个线程的坐标也随之更新：沿视图的变换链做增量更新（每个变换只根据坐标的增量更新自己的下层坐标，tensor_adaptor_coordinate.hpp 第 172 行起逆序遍历每个变换），不从头重算。对本例的 embed 和 pad 来说，这就是几次加法；遇到 merge 这类变换则有进位、借位的逻辑。

下面的例子不是归约，而是逐元素的 y = alpha · x：一个 block 负责 2 行组成的横条，窗口从第 0 列出发，每轮处理 2 × (64·kVec) 个元素，然后两个窗口一起往右挪一个 tile 宽。列数不是 tile 宽的整数倍也没关系——最后一块伸出去的部分由 pad 屏蔽（§2.3）。

// 例子：y = alpha · x，x、y 都是 rows × cols 的行主序矩阵。
// 一个 block（2 个 wavefront）负责 2 行组成的“横条”，窗口沿列方向一格一格往右滑。
template <index_t kVec>
__global__ void scale_strip_kernel(const float* x, float* y, float alpha, index_t rows, index_t cols) {
  constexpr index_t kTM = 2, kTN = 2 * 32 * kVec;          // tile：2 行 × (64·kVec) 列
  auto make_view = [&](auto* p) {
    return pad_tensor_view(
        make_naive_tensor_view<address_space_enum::global>(p, make_tuple(rows, cols), make_tuple(cols, 1),
                                                           number<kVec>{}, number<1>{}),
        make_tuple(number<kTM>{}, number<kTN>{}), sequence<true, true>{});
  };
  auto vx = make_view(x);
  auto vy = make_view(y);

  // 行 X0 = (lane 高位 2)，列 X1 = (warp 2, lane 低位 32, Y kVec)：一行横跨两个 wavefront
  constexpr auto dist = make_static_tile_distribution(
      tile_distribution_encoding<sequence<>,
                                 tuple<sequence<2>, sequence<2, 32, kVec>>,
                                 tuple<sequence<2>, sequence<1, 2>>,
                                 tuple<sequence<0>, sequence<0, 1>>,
                                 sequence<2>,
                                 sequence<2>>{});

  const index_t row0 = static_cast<index_t>(blockIdx.x) * kTM;
  auto wx = make_tile_window(vx, make_tuple(number<kTM>{}, number<kTN>{}), {row0, 0}, dist);
  auto wy = make_tile_window(vy, make_tuple(number<kTM>{}, number<kTN>{}), {row0, 0}, dist);

  const index_t n_steps = integer_divide_ceil(cols, kTN);
  for (index_t s = 0; s < n_steps; ++s) {
    auto tx = load_tile(wx);
    auto ty = tile_elementwise_in([&](float v) { return alpha * v; }, tx);   // 逐元素，结果同分布
    store_tile(wy, ty);
    move_tile_window(wx, {0, kTN});   // 两个窗口都往右挪一个 tile 宽
    move_tile_window(wy, {0, kTN});
  }
}

本机运行结果（通过 §3.5 的启动函数调用）：1×1、8×64、13×30、33×31、100×1001、7×4099、64×4096 全部逐位正确，输出两侧的哨兵完好。

这个例子的行方向全部由 P 认领（lane 高位 2），没有 Y。本机实测，这时对它调用 sweep_tile（Lab 2 §3.4 的逐元素遍历）会编译失败：implicit instantiation of undefined template 'ck_tile::impl::reverse_slice_sequence_impl<…>'。所以例子改用 tile_elementwise_in(f, t)（core/tensor/tile_elementwise.hpp 第 40 行）：对 t 的每个元素调用 f，返回同分布的新 tile，不在乎 Y 怎么分。给行方向补一个长度为 1 的 Y 段，sweep_tile 也能编译。

逐元素运算不在乎“谁和谁在一起”，所以这里怎么分都行：一行 64·kVec 列横跨两个 wavefront，行方向没有 Y。把它原样拿去做行归约，两条 §3.1–§3.2 的约束都会被违反——行方向没有 Y，block_tile_reduce 编译失败；就算补上 Y，同一行的部分和分在两个 wavefront 里，block_tile_reduce_sync 也合不起来。a3 的分布要你从约束出发自己设计。

把这个循环和 §3.1 中“累加进已有累加器”的 block_tile_reduce 重载放在一起想：如果每一步不是“算完就写”，而是把这一块归约进同一个累加器，循环结束后再做一次 sync、写一次结果——这就是沿长行做归约的骨架。只是分布、tile 形状和 block 大小都得换成满足 §3.1–§3.2 约束的那一套（见上面的 warn 框），这一步就是 a3 的设计。像这样在循环里反复从同一个（移动中的）窗口 load，正是 Lab 2 §4.3 第 3 问（load_tile(dst_tile, window) 重载）的使用场景，现在可以回头答它。

§3.4guaranteed vector length 与对齐

make_naive_tensor_view（和 make_naive_tensor_descriptor）的最后两个参数，Lab 2 称作“保证的最内维向量长度”和“保证的最内维 stride”。它们是你对 CK-Tile 许下的承诺：“沿最内维，从 V 的倍数开始的每 V 个元素，可以当成一个向量一次访问”。CK-Tile 不检查这个承诺，只是照着它生成指令：

  • 向量长度 = gcd(承诺的 V, 认领最内维最低段的那个 Y 的长度)（Lab 2 §3.2）。不承诺（省略或写 1）就是逐元素访问。
  • 越界检查以“一个向量”为单位：buffer_view.hpp 第 288–291 行的 get 只接受一个 bool is_valid_element；pad 变换计算的是向量第一个元素的坐标是否有效。right_pad 在计算向量长度时的注释（coordinate_transform.hpp 第 420–422 行）说得很清楚：“we allow pass through this vector length. If one need per-pixel check, should change the guaranteed vector length while creating the tensor view. It's up to runtime to check the padding length should be multiple of vector length”。

换句话说，承诺 V 时你必须保证：任何一个从 V 的倍数开始的向量，要么完全在一行之内，要么完全在一行之外。对行主序矩阵，这等价于“列数是 V 的倍数”——否则行尾那个向量会伸进下一行，而 pad 只检查它的第一个元素，拦不住。（列数是 V 的倍数、数组首地址又对齐时，每个向量的起始地址也恰好对齐到 V 个元素；对齐是另一件事，下面实验的结果里会看到，在 gfx942 上它不是出错的原因。）下面的实验把 §2.3 的 peek 改成承诺 V：一个 16 × 16 的窗口读 3 × 6 的矩阵（带 pad），6 是 2 的倍数、不是 4 的倍数。

// 16×16 的窗口读 3×6 的矩阵（带 pad），视图承诺最内维向量长度 kVec
template <index_t kVec>
__global__ void peek_vec(const float* in, float* dump, index_t rows, index_t cols) {
  auto v = pad_tensor_view(
      make_naive_tensor_view<address_space_enum::global>(in, make_tuple(rows, cols), make_tuple(cols, 1),
                                                         number<kVec>{}, number<1>{}),
      make_tuple(number<16>{}, number<16>{}), sequence<true, true>{});
  // 每个 lane 拿同一行里连续 kVec 个元素
  using Enc = std::conditional_t<kVec == 4,
      tile_distribution_encoding<sequence<>, tuple<sequence<16>, sequence<4, 4>>,
                                 tuple<sequence<1, 2>>, tuple<sequence<0, 0>>, sequence<2>, sequence<1>>,
      tile_distribution_encoding<sequence<>, tuple<sequence<2, 8>, sequence<8, 2>>,
                                 tuple<sequence<1, 2>>, tuple<sequence<1, 0>>, sequence<1, 2>, sequence<0, 1>>>;
  constexpr auto dist = make_static_tile_distribution(Enc{});
  auto w = make_tile_window(v, make_tuple(number<16>{}, number<16>{}), {0, 0}, dist);
  auto t = load_tile(w);
  auto vd = make_naive_tensor_view<address_space_enum::global>(
      dump, make_tuple(16, 16), make_tuple(16, 1), number<1>{}, number<1>{});
  auto wd = make_tile_window(vd, make_tuple(number<16>{}, number<16>{}), {0, 0}, dist);
  store_tile(wd, t);
}

  10  11  12  13  14  15   0   0         10  11  12  13  14  15  20  21
  20  21  22  23  24  25   0   0         20  21  22  23  24  25   0   0

V = 4 时，第 4–7 列这个向量的第一个元素（第 4 列）是有效的，于是整个向量被放行，读进了下一行开头的两个元素——pad 也拦不住。（第 2 行同一位置偏移已越过数组末尾，被硬件按 dword 屏蔽。另外，这里第 1 行的向量起始地址是 40 字节，不是 16 的倍数，本机的 buffer_load_dwordx4 照样读对了；所以在 gfx942 上，承诺错了的可见后果主要是“跨行”，而不是对齐异常。）

承诺对了的回报是什么？用 §3.3 的 scale_strip_kernel 在 8192 × 8192 上实测（GPU 空闲，每种 3 次取最好）：承诺 4 时汇编是 buffer_load_dwordx4 / buffer_store_dwordx4，有效带宽约 3.3 TB/s；承诺 2 时是 …_dwordx2，约 2.5 TB/s；承诺 1 时是 buffer_load_dword / buffer_store_dword，约 1.7 TB/s——差约两倍。（同进程测的 hipMemcpy D2D 拷贝只有约 2.1 TB/s，比这个 kernel 还慢，所以“相对拷贝带宽的比值”大于 1 并不奇怪：拷贝带宽是一个参照，不是上限。）

§3.5运行时分派到编译期配置

问题来了：向量长度必须是编译期常量（它是模板参数、决定了 tile 宽度和指令），而“列数是不是 V 的倍数”要到运行时才知道。解决办法是把 kernel 写成模板，两个版本都编译出来，在主机端按运行期条件选一个启动：

// 运行期分派：cols 是偶数时，才实例化并启动“承诺向量长度 2”的版本
void launch_scale_strip(const float* x, float* y, float alpha, int rows, int cols, hipStream_t stream) {
  const int grid = (rows + 1) / 2;                 // 每个 block 一个 2 行的横条（128 线程 = 2 个 wavefront）
  if (cols % 2 == 0)
    scale_strip_kernel<2><<<grid, 128, 0, stream>>>(x, y, alpha, rows, cols);
  else
    scale_strip_kernel<1><<<grid, 128, 0, stream>>>(x, y, alpha, rows, cols);
}

要点：

  • 两个实例 scale_strip_kernel<2> 和 <1> 都会被编译进程序（本机汇编里能看到两个 kernel 符号），代价是代码体积，不是运行时间。
  • 选择发生在主机端、kernel 启动之前；kernel 内部没有任何关于 V 的分支。
  • 模板参数不只决定视图的承诺，还连带决定了分布（Y 段长度）和 tile 宽度——一个编译期配置是一整套自洽的常量。例子只分了两档；要承诺 V = 4 需要什么条件、是否值得再加一档，按 §3.4 自己推，照样加分支即可。grid 和 block 的大小也由这套常量决定（这里每 block 2 行、128 线程），换一个分布就要跟着重算。
  • 条件要覆盖承诺的全部前提：这里数组来自 hipMalloc（首地址对齐），所以只检查列数。

自主设计：骨架只有空的 launch_ck_row_sum。你要决定一个 block 处理几行、行和列怎样分给 warp / lane / Y（一行不能跨 wavefront，§3.2；结果方向要留一个 Y，§3.1）、怎样沿列滑动窗口并累加（§3.3）、边缘怎样处理（§2.3）、什么时候可以承诺向量长度 4（§3.4）以及如何在运行时分派（§3.5）。

§4.2预告 Lab 4：warp GEMM 与 MFMA 的分布

MI308X 的 MFMA（Matrix Fused Multiply-Add）指令让一个 wavefront 的 64 个 lane 合作完成一个小矩阵乘，例如 32 × 32 × 8。指令规定了 A、B、C 三个小块分别以什么方式摆在 64 个 lane 的寄存器里——这恰好就是三个 tile_distribution_encoding。CK-Tile 把每种 MFMA 指令包装成一个“warp GEMM”，它的分布直接写在类型里：

using AWarpDstrEncoding = decltype(get_warp_dstr_encoding<Impl::kAMLane>());

往上往下翻，B、C 也各有一个 encoding。Lab 4 会读懂它们，然后做的正是 §2.5 演示过的事：用适合全局内存的分布把 A、B 搬进 LDS，再用 MFMA 规定的分布读出来喂给指令；C 的累加器就是一个按 MFMA 分布排布的 distributed tensor。本课的 layout（§1）、二维分布与 LDS（§2）、R 维与跨 lane 合并（§3）在那里会全部用上。
