# 审查提示词（每个 Lab 完成后并行派发 3 个 subagent）

## R1 学生视角走查
你是一名会用 C++、了解 GPU 大致概念、但没写过 HIP kernel 的学生（CK-Tile 模板元编程不熟）。仓库根目录 /mnt/raid0/WangTianle/workspace/HIP-tutorial。
**禁止读取 solutions/ 目录与任何 mutants。** 只读 {LAB}/tutorial.html（可用浏览器或直接读 HTML）、{LAB}/aK-*/README.md 与骨架文件。
任务：按顺序在一个临时拷贝中完成每个 Assignment（`cp -r {LAB} /tmp/r1-{LAB}` 后在拷贝中做；`common/` 用原路径），用 `make grade` 检查。
报告（中文）：每个 Assignment 卡住的地方与原因（讲义缺了什么、Hint 不够、知识跳跃、TODO 说明有歧义）；讲义中引用但不存在的小节；判分输出是否帮你定位问题；最终得分。不要修改原仓库。

## R2 判分对抗审查
你的目标是找出判分漏洞：写出"看起来对但实际错误"的实现，看 `{LAB}` 的测试能否抓住。可以读 solutions/ 和 test.cpp。
对每个 Assignment 至少尝试 4 种不同错误（越界、漏边界、错误下标、数据竞争、只对特定尺寸成立、偷懒的性能作弊如不计算直接返回、写错误位置后又被覆盖等）。
用 `python3 common/grade.py {LAB} --only aK` 在临时目录的拷贝上测试（不要改原仓库文件）。
同时检查是否存在"正确实现被判错"的情况（例如合理的不同 block 尺寸、不同求和顺序、不同 tile 选择）——至少写 2 个与参考答案结构不同的正确实现并确认满分。
报告：漏网的错误实现（附代码）、被误判的正确实现（附代码）、建议新增的测试/mutant。

## R3 技术准确性审查
核对 {LAB}/tutorial.html、README 与代码注释中的技术事实：gfx942/CDNA3 硬件参数（CU 数、wave 大小、LDS 大小与 bank 数、缓存层级、峰值带宽/算力的计算）、HIP API 语义、CK-Tile API 用法（对照 /opt/rocm/include/ck_tile 源码）。可用 rocminfo、hipcc 写小程序实测。
报告：每条错误/不严谨陈述的位置、原文、更正及依据（源码路径或实测输出）。

## R4 行文与术语审查

讲义按“行文规范”（CLAUDE.md）改写前后各审一次。每页四份独立审查：两份表述与术语、两份技术严谨性；另做一次全课程术语普查。审查对象是讲义 HTML 与按段编号的纯文本（每段一行，行首 `[§x.y ¶n]`，框体、图内文字、代码块分别标注），意见里的位置一律用这个段号。不改 § 编号与标题 id 是前提，不接受调整章节结构的建议。

**表述与术语审查**（以 CLAUDE.md“定位”里的学习者身份，按顺序读，不读 solutions/）检查五类问题：说人话（要读两遍的句子、一句多义、多层括号或破折号、先细节后结论、指代不清）、术语（首次出现未解释、前后叫法不一、自造译名、把代码名当普通名词）、超纲（用到前文没讲的概念）、冗余（打断主线的旁枝）、一致性（与讲义其他处矛盾）。不报个人偏好与技术对错。“必须改”= 学习者会读不懂或误解；“建议改”= 读得懂但费劲。每条给可直接替换的改法，细节多时说明主线写什么、哪些放进折叠框。

**技术严谨性审查**逐条核对硬件参数与行为、HIP API 与编译器语义、CK-Tile 用法、性能数字及其推论、代码片段，依据 `/opt/rocm/include`、CK-Tile 源码、仓库代码与 CLAUDE.md 的已知坑；需上机才能确认的写“需实测：怎么测”，不猜。错误、或把有条件成立写成总是成立并会误导学习者 → 必须改；可以更严谨但不影响使用 → 建议改（优先放折叠框）。同时反向检查：正文堆了太多限定和实测细节、主线读不下去，报“冗余”。

**术语普查**按课程顺序列出全部技术术语：推荐写法（HIP/AMD 通用英文术语保留英文，有通用中文说法的用中文，不自造译名）、其他写法及位置、首次出现位置、首次是否解释、一句话解释，再列出最需要统一的不一致处。结果整理为 `docs/glossary.md`。

**复审**（第 2、3 轮）输入是改写后的讲义、改写前后纯文本的 diff、上一轮整改清单和逐条回应。检查：上一轮“必须改”是否真正解决；回应里“不改”的理由是否成立；改动段落是否引入新问题（最常见的是为了好懂把有条件成立写成总是成立），是否又把正文写长写绕。已解决的不再报，没改动的段落不提新意见。

**输出格式**：先一个 jsonl 代码块，每行一条，字段为 id、loc（段号）、type、severity（必须改 / 建议改）、quote（逐字原文）、problem、fix（可直接替换的文字）、evidence（源码路径:行号、命令及输出或“需实测”）；复审另加 kind（未解决 / 驳回不成立 / 新问题），无问题时只写 `{"kind":"无"}`。之后是不超过 5 条的“总体问题”（复审省略），最后一行“结论：通过”或“结论：不通过”（有任一“必须改”即不通过）。多份审查的意见合并去重后，按“两份以上指出 = 高、一份必须改 = 中、一份建议改 = 低”标置信度；高、中逐条回应，低按行文规范自行判断。
