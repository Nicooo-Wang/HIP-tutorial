读懂 CK-Tile：从 C++ 编译期编程到第一个 tile kernel

Lab 1 里，每个 kernel 的第一行几乎都是你亲手推出来的下标公式：i = blockIdx.x * blockDim.x + threadIdx.x，然后是 if (i < n)。这一课换一种写法：不再计算每个线程该碰哪个元素，而是用类型描述“一块数据怎样分给一组线程”，让 CK-Tile 去生成下标、向量化访存和边界处理。为了读懂这种写法，先补一段 C++ 编译期编程，再写第一个 CK-Tile kernel。

预计阅读 80 分钟 · 对应 Assignment a1、a2 · 前置：Lab 1 讲义

§1为什么需要 CK-Tile

CK-Tile 是 AMD Composable Kernel（CK）库的新一代“tile 编程”接口，随 ROCm 安装在 /opt/rocm/include/ck_tile（本机 ROCm 7.2.0）。它是纯头文件库：没有 .so 要链接，#include "ck_tile/core.hpp" 就能用，所有名字都在命名空间 ck_tile 里。AMD 官方的 GEMM、FlashAttention（fmha）、MoE 等高性能 kernel 都用它写成。这一节先说清楚它要解决什么问题，再给一张源码地图。

§1.1手写 kernel 的四个痛点

回头看 Lab 1 的四个 Assignment：每一个都在回答同一个问题——哪个线程负责哪些数据——而答案都写成了散落在 kernel 各处的整数运算。问题规模一大，这种写法会在四个地方同时变难：

  1. 下标。向量加法只有一层映射（全局线程号 → 元素）；转置多了一层“tile 内坐标”；分块 GEMM 有 block → wavefront → 线程 → 每线程多个输出四层。每一层都要手推公式，任何一处写错，结果就错一片。
  2. 向量化。想让一条指令搬 16 字节，就得自己转成 float4、保证对齐、再为“最后不满 4 个”的尾部单独写一段（见下面的片段）。
  3. LDS 布局。Lab 1 §3.6 为了避开 bank conflict 加了 padding。换一种 padding 或 swizzle，所有读写 LDS 的下标都要跟着改。
  4. MFMA 布局。Lab 4 要用的矩阵指令（MFMA）规定了 A、B、C 小块在 64 个 lane 的寄存器里怎么摆，是一张需要查表的映射。手写时，从显存到 LDS 再到寄存器的每一步都要与它对齐。
// 手写向量化拷贝：每个线程拷贝 4 个连续 float；n 不是 4 的倍数时，尾部要单独处理
__global__ void copy4(const float* __restrict__ src, float* __restrict__ dst, int n) {
  int i = (blockIdx.x * blockDim.x + threadIdx.x) * 4;     // 本线程 4 个元素的起点
  if (i + 3 < n) {                                          // 4 个都在范围内：一条 16 字节访存
    *reinterpret_cast<float4*>(dst + i) = *reinterpret_cast<const float4*>(src + i);
  } else {                                                  // 尾部：逐个处理
    for (int k = i; k < n; ++k) dst[k] = src[k];
  }
}

这还只是一维拷贝。CK-Tile 的思路是把“数据怎样分给线程”从运算里抽出来，写成一个类型（tile distribution，§3.2）。有了这个类型，同一套 load_tile / store_tile 就能自动生成每个线程的地址、选择向量指令宽度、处理越界——上面这段 if/else 在 CK-Tile 里一行都不用写（§3.4 的例子会生成与它等价的 16 字节访存）。

类型在编译期就完全确定。把布局写进类型，编译器就能在编译期算出每个线程的寄存器怎样排、循环展开成几条指令、哪些检查可以省掉——运行时只剩真正必要的地址加法。代价是：你得能读懂“用类型做计算”的 C++。这正是 §2 要补的课。

§2C++ 速成：读懂 CK-Tile 需要的编译期编程

打开任何一个 CK-Tile 头文件，你会看到满屏的 template、number<…>{}、static_for、if constexpr 和 [&](auto i) {…}。它们服务于同一个目的：让尽可能多的计算发生在编译期。在 GPU 上这不只是“快一点”，而是关系到数据能不能留在寄存器里：

  • 寄存器没有“地址”，寄存器数组只能用编译期已知的下标访问。下标是运行期变量时，编译器只能退而求其次：本机实测，一个 8 个 float 的数组用运行期下标读一次，编译出 7 条 v_cndmask（逐个比较、挑选）；64 个 float 的数组则整个被搬进 272 字节的 scratch（每线程私有、但在显存里，很慢）。用编译期下标，两种情况都只是一次寄存器读。
  • tile 的大小、每个线程负责几个元素、循环几次，都在编译期确定，编译器就能把循环完全展开，把多次标量访存合并成一条向量指令。
  • 布局写错了（比如分块大小不整除），可以用 static_assert 在编译期就报出来，而不是跑出一堆错数。

下面六小节各对应 a1 的一道练习（E1–E6）。每节先讲规则，再给一个别的问题上的同类例子，最后摘一段 CK-Tile 的真实源码，让你确认“这正是它天天在用的写法”。本节所有代码片段都在本机用 hipcc -std=c++20 编译通过，其中 kernel 在 GPU 上实际运行过。片段里的 index_t 是 ck_tile::index_t（即 int32_t）。

§2.1constexpr 与折叠表达式

constexpr 函数是“参数都是常量时，可以在编译期求值”的函数。它同时也是普通函数——传运行期的值进去，就在运行期算。static_assert(条件) 要求条件是编译期常量，否则编译失败；它是检验“这件事是不是在编译期发生”的最好工具。

constexpr index_t ceil_div(index_t a, index_t b) { return (a + b - 1) / b; }

static_assert(ceil_div(1000, 256) == 4);        // 编译期就算出来并检查
constexpr index_t kBlocks = ceil_div(4096, 256);
float tmp[kBlocks];                             // 结果是编译期常量，可以当数组长度
int at_runtime(int n) { return ceil_div(n, 256); }   // 同一个函数，运行期也能用

参数包（parameter pack）。template <index_t... Is> 声明了“任意多个 index_t 模板参数”，合起来叫 Is。CK-Tile 的 sequence<Is...> 就是一个什么数据都不存的空结构体，它的全部信息都在模板参数里——一串编译期整数。把 sequence<2, 3, 4>{}（一个空对象）传给形参类型为 sequence<Is...> 的函数，编译器就推导出 Is = 2, 3, 4。

包不能直接下标访问，只能展开：在某个表达式模式后面写 ...，这个模式就对包里的每个元素复制一份，用逗号隔开。sizeof...(Is) 则给出包里有几个元素。

template <index_t... Is>
constexpr index_t count(sequence<Is...>) {
  return sizeof...(Is);                 // 包里有几个元素
}
template <index_t... Is>
constexpr index_t first_or_minus1(sequence<Is...>) {
  const index_t arr[] = {Is..., -1};    // 包展开：{2, 3, 4, -1}
  return arr[0];
}
static_assert(count(sequence<2, 3, 4>{}) == 3);
static_assert(first_or_minus1(sequence<2, 3, 4>{}) == 2);
static_assert(first_or_minus1(sequence<>{}) == -1);   // 空包：数组里只剩 -1

折叠表达式（fold expression，C++17）把整个包用同一个二元运算符“串起来”。它有四种形式，括号必不可少。以 Is = 2, 3, 4、运算符 op 为例：

四种折叠表达式（init 是你提供的初值）
写法名字展开成空包时
(Is op ...)一元右折叠2 op (3 op 4)只有 &&（得 true）、||（得 false）、逗号允许，其余编译错误
(... op Is)一元左折叠(2 op 3) op 4
(Is op ... op init)二元右折叠2 op (3 op (4 op init))结果就是 init
(init op ... op Is)二元左折叠((init op 2) op 3) op 4

“包”的位置也可以是一个含包的表达式，比如 (Is > 0) 或 (Is % 2 == 0 ? 1 : 0)——展开时这个表达式对每个元素各算一次：

template <index_t... Is>
constexpr bool all_positive(sequence<Is...>) {
  return (true && ... && (Is > 0));     // 二元左折叠，初值 true
}
template <index_t... Is>
constexpr index_t count_even(sequence<Is...>) {
  return (index_t{0} + ... + (Is % 2 == 0 ? 1 : 0));   // 对“每个元素的表达式”折叠
}
static_assert(all_positive(sequence<3, 1, 4>{}));
static_assert(!all_positive(sequence<3, 0, 4>{}));
static_assert(all_positive(sequence<>{}));             // 空包：结果是初值 true
static_assert(count_even(sequence<3, 2, 8, 5>{}) == 2);
static_assert(count_even(sequence<>{}) == 0);          // 空包：结果是初值 0

初值该取什么？它必须是这个运算的单位元——和任何数运算后都不改变那个数的值（加法是 0，逻辑与是 true）。这样有元素时它不影响结果，没有元素时它自己就是正确答案。如果省掉初值写成一元折叠，空包会直接编译失败：

error: unary fold expression has empty expansion for operator '+' with no fallback value
template <index_t... Xs, index_t... Ys>
CK_TILE_HOST_DEVICE constexpr bool operator==(sequence<Xs...>, sequence<Ys...>)
{
    return ((Xs == Ys) && ...);
}

两个 sequence 相等的判断：(Xs == Ys) 里同时出现了两个包，它们按位置同步展开成 (X0 == Y0) && (X1 == Y1) && …（两个包长度必须相同）。空 sequence 比较时，&& 的一元折叠给出 true。§2.3 的 static_for（最常用的 static_for<0, N, 1> 那个特化）内部则用到了逗号折叠（core/utility/functional.hpp 第 70 行）。

对应 a1 的 E1（product）。

§2.2array 与编译期计算

包适合“对每个元素做同一件事”，但不适合“从后往前走、边走边累积”这类需要下标和循环的计算。这时的标准做法是：先把包展开进一个数组，再在 constexpr 函数里像写普通 C++ 一样用循环。C++14 起，constexpr 函数里可以有局部变量、for 循环和 if，只要最终能在编译期算完。

返回值用 ck_tile::array<T, N>：一个定长数组，和 std::array 类似，但可以在 host 和 device 两边使用。它有两种下标写法——CK-Tile 的习惯是 a(i) 用来写、a[i] 用来读：

constexpr auto make_squares() {
  ck_tile::array<index_t, 4> a{};      // {} 把 4 个元素都初始化为 0
  for (index_t i = 0; i < 4; ++i)
    a(i) = i * i;                      // 写：CK-Tile 习惯用 a(i)
  return a;
}
constexpr auto sq = make_squares();
static_assert(sq[3] == 9);             // 读：a[i]
static_assert(sq.size() == 4);

下面是一个完整的“包 → 数组 → 循环”例子：给定结构体各字段的字节数，算出每个字段的起始偏移（每个字段前面所有字段大小之和，即“排他前缀和”）。注意三个步骤：

// 字段大小 <4, 2, 8, 4> → 偏移 {0, 4, 6, 14}
template <index_t... Sizes>
constexpr auto field_offsets(sequence<Sizes...>) {
  constexpr index_t N = sizeof...(Sizes);
  constexpr index_t sz[N] = {Sizes...};      // ① 包 → 普通数组，才能用下标和循环
  ck_tile::array<index_t, N> off{};
  index_t running = 0;                       // ② 累加器
  for (index_t i = 0; i < N; ++i) {          // ③ 从第 0 个往后走
    off(i) = running;                        //    先记下“前面之和”
    running += sz[i];                        //    再把自己加进去
  }
  return off;
}
constexpr auto off = field_offsets(sequence<4, 2, 8, 4>{});
static_assert(off[0] == 0 && off[1] == 4 && off[2] == 6 && off[3] == 14);
static_assert(std::is_same_v<decltype(off), const ck_tile::array<index_t, 4>>);

初值列表比数组短时，std::array 把剩下的元素补 0，而 ck_tile::array 用最后一个值补齐：ck_tile::array<index_t, 4>{1, 2} 是 {1, 2, 2, 2}（见 core/container/array.hpp 第 53–73 行的构造函数和注释 “behavior different from std”）。想要全 0，就写空的 {}，它调用第 52 行的默认构造函数。

倒着走的循环 for (i = N - 1; i >= 0; --i) 一定要用有符号的下标类型（index_t 就是有符号的 int32_t）。如果写成 size_t 或 unsigned，i >= 0 永远为真，0 再减 1 会绕回一个巨大的数。在 constexpr 求值里这是越界访问，编译器会直接拒绝。本机实测，像 E2 这样的函数模板，错误报在调用处：constexpr variable 's' must be initialized by a constant expression（变量名是你调用处的那个变量），下一行附注 cannot refer to element 18446744073709551615 of array of 3 elements in a constant expression。如果下标在用之前先被转成了 index_t，附注里的数字会是 -1。看到这种巨大的数或 -1，就去检查倒序循环的下标类型。

stride 是什么。多维张量在内存里终究是一维的。一个 D 维张量的元素 (i0, i1, …) 在内存中的偏移是

offset = i0 × stride0 + i1 × stride1 + … // stride_k：第 k 维坐标加 1 时，偏移加多少

你在 Lab 1 §3.2 已经用过二维的情形：rows × cols 的行主序矩阵，(r, c) 的偏移是 r × cols + c，也就是 strides = (cols, 1)。行主序的意思是最后一维变化最快（stride 为 1）；紧密排列（packed）的意思是元素之间没有空隙。如果这个矩阵是另一个更宽的矩阵（每行 ld 个元素）中的一块，它就不紧密了，strides 是 (ld, 1)。§3.1 的 make_naive_tensor_view 正是用“各维长度 + 各维 stride”来描述一块内存的；一维连续数组的 strides 就是 (1)。三维及以上的紧密行主序 stride 怎么算，就是 a1 E2 要你写的。

CK_TILE_HOST_DEVICE static constexpr index_t at(index_t I)
{
    // the last dummy element is to prevent compiler complain about empty array, when mSize = 0
    const index_t mData[size() + 1] = {Is..., 0};
    return mData[I];
}

sequence 用运行期下标取元素的方法，正是“包 → 数组”：展开进局部数组再下标。末尾多放一个 0，是为了空包时数组长度不为 0（C++ 不允许长度为 0 的数组）。另见 core/container/array.hpp 第 117–119 行：operator[] 和 operator() 都返回元素的引用，后者旁边的注释 “TODO: compatible” 说明它是为兼容旧写法保留的——CK-Tile 内部大量用 a(i) = … 写数组，例如 core/tensor/tile_distribution.hpp 第 301 行的 rh_major_minor_to_hidden_ids(0)(i) = hidden_dim_cnt;（数组的数组，连续两次下标）。

对应 a1 的 E2（row_major_strides）。

§2.3number<N> 与 static_for

一个关键限制：函数参数永远不是常量表达式。哪怕调用时传的是字面量 4，函数体内的形参 n 也不能当数组长度或模板参数。但参数的类型是编译期确定的。于是 CK-Tile 把数“放进类型里”：

template <auto v>
struct constant
{
    using value_type                  = decltype(v);
    using type                        = constant; // using injected-class-name
    static constexpr value_type value = v;
    CK_TILE_HOST_DEVICE constexpr operator value_type() const noexcept { return value; }
    CK_TILE_HOST_DEVICE constexpr value_type operator()() const noexcept { return value; }
    CK_TILE_HOST_DEVICE static constexpr bool is_static() { return true; }
};
// …
template <index_t v>
using number = constant<v>;

number<4> 是一个没有任何数据成员的类型，“4”只存在于它的模板参数和 static constexpr 成员 value 里。第 17 行的转换运算符让它能在需要整数的地方自动变成 4。

constexpr auto four = number<4>{};
static_assert(decltype(four)::value == 4);   // 值在类型里
static_assert(four.value == 4);              // 也可以通过对象取 static 成员
constexpr index_t as_int = four;             // 能隐式转成 index_t
static_assert(as_int == 4);
static_assert(sizeof(four) == 1);            // 空对象：运行时不携带任何数据

所以有两种“用法”要分清：

  • 当整数用：out[k]、base + k、2 * k。k 通过转换运算符变成整数参与运算，和普通 int 没区别。
  • 当编译期常量用：模板参数、数组长度、constexpr 变量的初值、static_assert。这时请写 k.value（或 §2.6 的 decltype(k)::value）：value 是 static constexpr 成员。只要 k 是按值传进来的（像 static_for 的 lambda 参数 auto k 那样），k.value 就是常量表达式；k 是引用参数（const auto& k）时则不行，要从类型里取，§2.6 会专门讲这个坑。

static_for 把一个“函数”对 Begin、Begin+Inc、…（不含 End）各调用一次，并把每次的循环变量以 number<i>{} 的形式传进去。写法是先构造一个对象 static_for<0, N, 1>{}，再用一个 lambda 调用它：

ck_tile::static_for<0, 4, 1>{}(f); // ≡ f(number<0>{}); f(number<1>{}); f(number<2>{}); f(number<3>{});

[捕获](参数) { 函数体 } 定义一个匿名函数对象。[&] 表示函数体里用到的外部变量都按引用捕获（能读也能改），[=] 是按值拷贝。参数类型写成 auto 的 lambda 叫泛型 lambda（§2.6 细讲）：static_for 每次传进来的 number<i> 类型都不同，所以参数必须是 auto。

下面的 kernel 让每个线程把自己负责的 N 个连续元素在寄存器里反序（不是 a1 的题目，但用到了同样的两种用法）：

template <index_t N>
__global__ void reverse_chunks(const float* in, float* out) {
  const index_t base = (blockIdx.x * blockDim.x + threadIdx.x) * N;
  float r[N];                                    // 寄存器数组
  ck_tile::static_for<0, N, 1>{}([&](auto k) {   // k 的类型：number<0>、number<1>、…
    r[k] = in[base + k];                         // k 隐式转成整数，当普通下标用
  });
  ck_tile::static_for<0, N, 1>{}([&](auto k) {

§2.4if constexpr

普通 if 在运行期选分支，但两个分支都必须能编译。在模板里，这常常做不到：同一段代码对 float 和对一个容器类型要做完全不同的事。if constexpr (条件) 要求条件是编译期常量，并且在模板实例化时直接丢弃没被选中的分支——那个分支不会被实例化，里面的代码对当前类型不合法也没关系。

template <class T>
constexpr const char* kind() {
  if constexpr (std::is_same_v<T, ck_tile::half_t>) return "fp16";
  else if constexpr (std::is_floating_point_v<T>)   return "其它浮点";
  else                                              return "非浮点";
}

条件里常见的“编译期就知道的量”：类型判断（std::is_same_v<A, B>、std::is_floating_point_v<T> 等，来自 <type_traits>）、sizeof(T)（单位是字节）、模板参数、number 的 .value。ck_tile::half_t 是 CK-Tile 的 fp16 类型。

“不被实例化”有多重要，看这个例子：

}

为什么下标必须是 number<I>？因为 at 的返回类型取决于下标：第 0 个是 int，第 1 个是 float。C++ 函数的返回类型必须在编译期确定，所以下标只能是编译期的值——放在类型里传进去。用运行期的 int 当下标，找不到匹配的重载：

  index_t cnt = 0;

§2.6泛型 lambda 与 decltype(a)::value

参数类型写成 auto 的 lambda 是泛型 lambda，相当于一个带模板 operator() 的函数对象：每用一种新的参数类型调用它，编译器就生成一个新版本。

constexpr auto twice = [](auto x) { return x + x; };   // 每种参数类型生成一个版本
static_assert(twice(3) == 6 && twice(1.5) == 3.0);

decltype(a) 给出变量 a 的声明类型。当 a 的类型是 number<6> 时，decltype(a)::value 就是那个类型的 static constexpr 成员 6——它是常量表达式，与 a 是“运行期的函数参数”毫不矛盾，因为我们根本没有读 a 这个对象，只读了它的类型。于是 lambda 可以把计算结果再放回类型里返回：

  return bool_constant<decltype(a)::value % 2 == 0>{};      // 值从参数的“类型”里取

static_assert(std::is_same_v<decltype(is_even(number<6>{})), bool_constant<true>>);
static_assert(std::is_same_v<decltype(is_even(number<7>{})), bool_constant<false>>);

buffer 寻址：越界屏蔽从哪里来。Lab 1 的 kernel 用的是普通的全局访存指令（global_load_dword 等），每个 lane 给出一个完整的 64 位地址，硬件不知道数组有多长，所以必须自己写 if (i < n)。AMD GPU 还有另一类访存指令：buffer 指令。它的地址由两部分组成：

  • 一个 128 位的资源描述符（buffer resource），放在 4 个标量寄存器（SGPR）里，整个 wavefront 共用。里面有基地址和这块缓冲区的字节长度（range）。
  • 每个 lane 自己的字节偏移，放在向量寄存器（VGPR）里。

硬件会拿每个 lane 的偏移与 range 比较，超出范围的访问被屏蔽，不会碰到缓冲区之外的内存。CK-Tile 对 address_space_enum::global 的视图就用 buffer 指令，range 设为“元素总数 × 元素字节数”，也就是 n × 4 字节。

range 检查以 dword（4 字节）为单位。float 一个元素正好一个 dword，所以本课里“部分越界的向量被逐元素屏蔽”成立。fp16 / bf16（2 字节）、int8（1 字节）这类小类型就不同了：只要一个 dword 有一部分越界，整个 dword 都被屏蔽，连同其中合法的元素。本机实测 fp16、每线程 8 个元素的一维视图：n = 505 时，合法的第 504 个元素 load 读回 0、store 没有写进去；n = 506 时一切正常。以后用这类小类型时，总字节数不是 4 的倍数（fp16 即 n 为奇数）的用例要特别留意。

对本课用的 naive 视图，越界屏蔽完全由这条硬件 range 检查完成，range 由视图长度 n 决定。CK-Tile 在软件层也会为每次访问算一个“坐标是否有效”的标志（tensor_view.hpp 第 88 行的 coordinate_has_valid_offset_assuming_top_index_is_valid）并交给 buffer view，但注意名字里的 assuming_top_index_is_valid：它假定窗口里的坐标本身在范围内，只检查 pad 这类“合法坐标也可能映射到无效位置”的变换。naive 视图里没有这类变换，这个标志在编译期就是常量 true，会被优化掉（本机汇编里没有为它生成任何选择指令 v_cndmask）；以后用到 pad_tensor_view 时它才真正起作用。所以你在 kernel 里不需要也不应该写 if (i < n)，但原因是 buffer 指令，不是软件判断。至于“越界的读到底返回什么值、越界的写具体怎样被丢掉”，留给 a2 的书面问题 2：从 buffer_view.hpp 里 address_space_enum::global 那个特化的 get、set 出发，一路追到 core/arch/amd_buffer_addressing.hpp 里真正发出 buffer 指令的函数。

§3.2tile distribution encoding

这是 CK-Tile 最核心、也最需要花时间的概念。问题是：一个 tile 有若干元素，一个 block 有若干线程，哪个线程拿哪些元素、拿到后放在自己的第几个寄存器里？Lab 1 用公式回答；CK-Tile 用一个纯编译期的类型 tile_distribution_encoding 回答。它用到四类“维度”：

R / H / P / Y 的含义（X 指 tile 本身的维度：一维 tile 只有 X0）
记号名字含义
HHierarchical（分层）把每个 X 维的长度拆成若干段的乘积，例如 512 = 2 × 64 × 4。各段像行主序坐标一样组合回 X：x = h0·(H1·H2) + h1·H2 + h2。
PPartition（划分）“谁”：分给 P 的段，坐标由线程身份决定。不同线程拿到不同的段坐标。
YYield（产出）“每个线程拿几个”：分给 Y 的段，坐标在线程内部遍历，对应线程自己的寄存器。一个线程持有的元素个数 = 所有 Y 长度之积。
RReplicate（复制）不属于 tile 的额外维度。分给 R 的 P 坐标不同的线程，持有完全相同的一份数据（复制）。不需要复制时为空 sequence<>。

一个合法的、每个元素恰好归一个线程的分布，要求 H 的每一段恰好被一个 P 或一个 Y 认领。认领关系用“(major, minor) 地址”写：major 选是哪一组——0 表示 R，k ≥ 1 表示第 k−1 个 X 维的 H；minor 选这一组里的第几段（从 0 数）。tile_distribution_encoding 的 6 个模板参数就是：

template <typename RsLengths_,    // sequence<...>
          typename HsLengthss_,   // tuple<sequence<...>, ...>
          typename Ps2RHssMajor_, // tuple<sequence<...>, ...>
          typename Ps2RHssMinor_, // tuple<sequence<...>, ...>
          typename Ys2RHsMajor_,  // sequence<...>
          typename Ys2RHsMinor_>  // sequence<...>
struct tile_distribution_encoding
  1. R 的各段长度：一个 sequence。
  2. H：tuple，每个 X 维一个 sequence，列出这一维拆成的各段长度。
  3. P → major：tuple，每个 P 维一个 sequence（一个 P 维可以认领多段，见本节后面的二维例子）。
  4. P → minor：与上一项形状完全相同，逐项给出段号。
  5. Y → major：一个 sequence，每个 Y 维一项（每个 Y 维只认领一段）。
  6. Y → minor：与上一项一一对应的段号。

P 维有几个、各代表什么？这不是随你定义的：线程的“身份”由 §2.4 摘过的那段源码决定（tile_distribution.hpp 第 94–107 行）——P 维只能是 1 个或 2 个。1 个时，P0 = lane id（0–63）；2 个时，P0 = warp id（threadIdx.x / get_warp_size()，gfx942 上就是 threadIdx.x / 64，即 block 内第几个 wavefront），P1 = lane id。

名字。CK-Tile 源码沿用 “warp” 一词，但指的就是本课程的 wavefront（gfx942 上 64 个 lane），不是 CUDA 的 32 线程 warp（Lab 0 §2.2 术语表）。get_warp_id() 就是你在 Lab 1 §4.4 算过的 wave_id，get_lane_id() 就是 lane。下文的 warp id、kWarps、以后的 “warp GEMM” 都按这个意思读。

为什么这里可以写 64。Lab 1 §4.3 说过：不要写死 wavefront 宽度，一律从 warpSize 推出；而 warpSize 在 HIP（ROCm 7.2）里是运行时值。tile distribution 却是一个编译期类型——lane 认领的段长（例如下面的 64）必须是编译期常量，用不了 warpSize。CK-Tile 的办法是自己提供一个 constexpr 函数（core/arch/arch.hpp 第 63–70 行）：

CK_TILE_HOST_DEVICE constexpr index_t get_warp_size()
{
#if defined(__GFX9__) || !defined(__HIP_DEVICE_COMPILE__)
    return 64;
#else
    return 32;
#endif
}

它按编译目标决定宽度：gfx9 系列（含本机的 gfx942）返回 64，其他架构返回 32；第 106 行的 get_warp_id() 也写的是 threadIdx.x / get_warp_size()，不是 / 64。本课程只编 --offload-arch=gfx942，所以 64 是确定的，作业骨架里的 kLanes = 64 等常量就是这样来的。两条原则合起来：运行期代码（循环、下标）用 warpSize；编译期布局（分布、数组长度）用 get_warp_size()，或者写 64 并加上 static_assert(… == ck_tile::get_warp_size()) 让换架构时编译报错，而不是悄悄算错。

只写 1 个 P 维时，线程只按 lane id 区分。block 里如果有不止一个 wavefront，它们的 lane id 都是 0–63，于是每个 wavefront 拿到的是同一批元素。本机实测：128 线程的 block，用 1 个 P 维、H = (128, 2)（P 认领第 0 段、Y 认领第 1 段）存一个 256 元素的 tile，结果元素 128–255 没有任何线程写；换成 load 再看每个线程拿到了什么，线程 64（wavefront 1 的 lane 0）拿到的是元素 0、1，与线程 0 完全相同——元素 0–127 被两个 wavefront 各处理了一遍。只有 lane id 能对上 h0 < 64 的那部分有人负责。所以：block 只有一个 wavefront 时，1 个 P 维够用；block 有多个 wavefront、又要它们分摊不同的数据时，需要 2 个 P 维，并让 P0（warp id）认领 H 中代表“第几个 wavefront”的那一段。

本节的例子。block 只有 1 个 wavefront，所以 1 个 P 维（lane）就够。512 个元素拆成 H = (2, 64, 4)：第 0 段“第几轮”给 Y0，第 1 段“第几个 lane”给 P0，第 2 段“轮内第几个”给 Y1：

// 节选自 §3.4 的完整 kernel
constexpr auto dist = make_static_tile_distribution(
    tile_distribution_encoding<sequence<>,                            // R：不复制
                               tuple<sequence<kRepeat, kThreads, kVec>>, // H：X0 = 2 × 64 × 4
                               tuple<sequence<1>>,                    // P0 → major 1（X0 的 H）…
                               tuple<sequence<1>>,                    //      … minor 1（第 1 段）
                               sequence<1, 1>,                        // Y0、Y1 → major 1 …
                               sequence<0, 2>>{});                    //      … minor 0、2（第 0、2 段）

make_static_tile_distribution 把编码“编译”成真正的分布对象（一组编译期的坐标变换）。读法：P0 的 major/minor 各是一个只含一项的 sequence，因为这个 P 维只认领一段；两个 Y 的 major 都是 1、minor 分别是 0 和 2。检查一遍：三段都被认领，且各只一次。

为什么这样排？看同一轮里的一条指令：64 个 lane 各取 4 个连续 float（16 字节），lane 之间首尾相接，合起来是 1024 个连续字节——完全合并的访存。CK-Tile 为每个 Y 维算一个“安全向量长度”，再从在内存里连续（stride 为 1）的 Y 维中挑安全向量长度最大的那个做向量访问（core/tensor/tile_window_base.hpp 第 152–170 行）。对认领 X 最低位一段的 Y 维，安全向量长度 = gcd(视图承诺的向量长度, 这一段的长度)，而且视图必须承诺最后一维 stride 为 1——这就是 §3.1 最后两个参数的用处。这里选中的是 Y1：它认领的 h2 正是 X0 最低位的一段，gcd(4, 4) = 4，即 4 个 float = 16 字节，正是 a1 E4 里 float 的那个数字。本机实测：视图承诺 8 时结果仍是 gcd(8, 4) = 4，承诺 2 时是 2，不承诺时是 1。惯例上把这一维放在 Y 的最后，这样它在线程缓冲区里也是连续的。

设计一个 encoding 时，可以按这张清单自查：

  1. 每个 X 维的 H 各段之积 = tile 在这一维的长度。
  2. H 的每一段恰好被一个 P 或一个 Y 认领，不重不漏。
  3. P 维的个数与 block 的形状相符：block 只有一个 wavefront 用 1 个，多个 wavefront 用 2 个（warp, lane）。
  4. P0=warp 认领的段长之积 = block 里的 wavefront 数；lane 认领的段长之积 = 64（即 get_warp_size()）。否则要么有线程闲着，要么有线程的坐标落到 H 的范围之外。
  5. 让一个 Y 维认领 X 最低位的一段（惯例上放在 Y 的最后），它在内存里才连续、才能向量化。

R 在 a2 里用不到，但会在后面的 GEMM 中出现（例如每个 wavefront 都需要同一块 B）。下面是一个本机运行过的例子：128 线程（2 个 wavefront），一个 128 元素的 tile，两个 wavefront 各持有完整的一份。它有 2 个 P 维：P0（warp id）认领 R 的第 0 段，P1（lane id）认领 H 的第 0 段。

using RepEnc = tile_distribution_encoding<
    sequence<2>,                        // R：复制 2 份
    tuple<sequence<64, 2>>,             // H：X0 = 64 × 2
    tuple<sequence<0>, sequence<1>>,    // P0 → R …， P1 → X0 的 H …
    tuple<sequence<0>, sequence<0>>,    //   … 第 0 段，      … 第 0 段
    sequence<1>,                        // Y0 → X0 的 H …
    sequence<1>>;                       //   … 第 1 段

实测 load 之后：线程 0 和线程 64 手里都是元素 (0, 1)，线程 63 和线程 127 都是 (126, 127)。

二维 tile 时，常把一个 wavefront 的 64 个 lane 排成“4 行 × 16 列”。这时 lane id 要同时决定行坐标里的一段和列坐标里的一段，所以这个 P 维的 major/minor 各有两项。下面是一个本机运行过的例子：4 × 64 的行主序 tile，1 个 wavefront，每个线程拿同一行里连续的 4 个元素。

using Enc2D = tile_distribution_encoding<
    sequence<>,                                // R：不复制
    tuple<sequence<4>, sequence<16, 4>>,       // H：X0（行）= 4，X1（列）= 16 × 4
    tuple<sequence<1, 2>>,                     // P0（lane）→ X0 的 H 和 X1 的 H …
    tuple<sequence<0, 0>>,                     //   … 各自的第 0 段
    sequence<2>,                               // Y0 → X1 的 H …
    sequence<1>>;                              //   … 第 1 段

一个 P 维认领的多段，也像行主序坐标一样拆分 lane id，先列出的段是高位：lane = 行 × 16 + 列组。实测 lane 0–15 拿第 0 行，lane 16–31 拿第 1 行……lane 17 拿第 1 行的第 4–7 列。

下面的小部件把“一维 tile、H 拆成 (wavefront 数, lane 数, 每线程个数) 三段”这一类分布画了出来，你可以改参数、点格子看任意元素的归属，并切换到“1 个 P 维”观察 warp id 不参与时发生了什么。lane 数允许选比 64 小的值，只是为了让图看得清；真实硬件上一个 wavefront 永远是 64 个 lane。

对应 a2 的 a2-2（encoding）。

§3.3tile window 与原点

tensor view 描述整个数组，distribution 描述一个 tile 内部怎么分。tile window 把两者接起来：在视图上框出“本 block 负责的那一块”，并记住用哪个分布去访问它。

// 节选自 §3.4 的完整 kernel
const index_t origin = static_cast<index_t>(blockIdx.x) * kTile;
auto wx = make_tile_window(vx, make_tuple(number<kTile>{}), {origin}, dist);
auto wy = make_tile_window(vy, make_tuple(number<kTile>{}), {origin}, dist);
template <typename TensorView_,
          typename WindowLengths_,
          typename StaticTileDistribution_,
          index_t NumCoord = 1>
CK_TILE_DEVICE constexpr auto
make_tile_window(const TensorView_& tensor_view,
                 const WindowLengths_& window_lengths,
                 const multi_index<TensorView_::get_num_of_dimension()>& origin,
                 const StaticTileDistribution_& tile_distribution,
                 number<NumCoord> = {})

四个参数：① 视图；② 窗口长度，一个装着 number<…> 的 tuple——编译期常量，必须与分布的 tile 大小（H 各段之积）一致；③ 原点，类型是 multi_index<维数>（即 ck_tile::array<index_t, 维数>），是运行期的值，通常直接写成花括号列表 {…}；④ 分布。第五个参数是性能调优用的，保持默认。

原点是这个窗口第一个元素在视图中的坐标。一维时就是“前面所有 block 已经处理了多少个元素”——和 Lab 1 的 blockIdx.x * blockDim.x 是同一个思路，只是现在一个 block 负责的是 kTile 个元素，不是 blockDim.x 个。

原点要求 index_t（有符号 32 位）。如果直接写 {blockIdx.x * kTile}，乘积是 unsigned int，而花括号初始化禁止窄化转换（unsigned → int 可能丢值），编译失败：

error: non-constant-expression cannot be narrowed from type 'unsigned int' to 'value_type' (aka 'int') in initializer list [-Wc++11-narrowing]
note: insert an explicit cast to silence this issue

照提示先 static_cast<index_t>(blockIdx.x) 再乘。

一个 kernel 里可以有任意多个窗口。逐元素运算时，所有输入、输出的窗口用同一个原点和同一个分布，于是同一个线程在每个窗口里拿到的都是“相同下标”的元素——这正是 c[i] = a[i] + b[i] 里三个 [i] 相同的含义。（窗口也可以移动：move_tile_window 在后面的 GEMM 里用来沿 K 方向滑动，本课用不到。）

对应 a2 的 a2-3（窗口原点与 3 个窗口）。

§3.4load_tile / distributed tensor / sweep_tile / store_tile

前三件都只是描述。真正搬数据的是这几个函数：

  • load_tile(window)：按窗口的分布，把本线程负责的元素从显存读进寄存器，返回一个 distributed tensor（类型 static_distributed_tensor<T, 分布>）。它是“整个 tile 在所有线程手里的分布式表示”；从单个线程看，它就是一个长度为 ∏Y 的寄存器数组（thread buffer），例子里是 2 × 4 = 8 个 float。
  • make_static_distributed_tensor<T>(dist)：按分布创建一个 distributed tensor（元素类型 T 必须显式写在尖括号里），通常用来装输出。它的寄存器没有初始化（不是清零），要先把每个元素写一遍再用。
  • sweep_tile(t, f)：对本线程持有的每一个元素调用一次 f(idx)。idx 是一个编译期的“分布式下标”（类型里编码了 Y 坐标），用它读 t[idx]、写 t(idx)——与 §2.2 的 array 同一个习惯。同一个 idx 可以用在任何一个分布相同的 distributed tensor 上，表示“同一个位置”。
  • store_tile(window, t)：把 distributed tensor 按窗口的分布写回显存。
template <typename TileDistributedIndices>
CK_TILE_HOST_DEVICE constexpr const DataType& operator[](TileDistributedIndices) const
{
    static_assert(is_static_v<TileDistributedIndices>,
                  "wrong! Tile Distributed Indices should be static");

    constexpr auto y_idx = get_tile_distribution().get_y_indices_from_distributed_indices(
        TileDistributedIndices{});

    return thread_buf_[number<ThreadTensorDesc{}.calculate_offset(y_idx) / PackedSize>{}];
}

和 tuple 的 at(number<I>) 一样，参数没有名字——下标完全在类型 TileDistributedIndices 里。由它在编译期算出 Y 坐标、再算出寄存器数组里的偏移，最后用 number<偏移> 去取 thread_buf_。这就是 §2 开头说的“寄存器数组只能用编译期下标”在 CK-Tile 里的落实。第 126 行的 operator() 是对应的可写版本。

其余三个函数的签名很短，值得各看一眼：load_tile.hpp 第 21–27 行（转手调用 tile_window.load()）、static_distributed_tensor.hpp 第 141–146 行（make_static_distributed_tensor）、store_tile.hpp 第 64–77 行（注意它的窗口参数是非 const 引用，所以要传一个普通的局部变量）。

下面是完整的 kernel 与启动函数，四件套各占几行：

#include <hip/hip_runtime.h>
#include "ck_tile/core.hpp"
using namespace ck_tile;

constexpr index_t kThreads = 64;                         // 1 个 wavefront
constexpr index_t kRepeat  = 2;                          // 每个线程做 2 轮
constexpr index_t kVec     = 4;                          // 每轮连续 4 个 float（16 字节）
constexpr index_t kTile    = kRepeat * kThreads * kVec;  // 每个 block 处理 512 个元素

__global__ void scale_kernel(const float* x, float* y, float alpha, index_t n) {
  // §3.1 tensor view
  auto vx = make_naive_tensor_view<address_space_enum::global>(
      x, make_tuple(n), make_tuple(1), number<kVec>{}, number<1>{});
  auto vy = make_naive_tensor_view<address_space_enum::global>(
      y, make_tuple(n), make_tuple(1), number<kVec>{}, number<1>{});

  // §3.2 tile distribution
  constexpr auto dist = make_static_tile_distribution(
      tile_distribution_encoding<sequence<>,                            // R：不复制
                                 tuple<sequence<kRepeat, kThreads, kVec>>, // H：X0 = 2 × 64 × 4
                                 tuple<sequence<1>>,                    // P0 → major 1（X0 的 H）…
                                 tuple<sequence<1>>,                    //      … minor 1（第 1 段）
                                 sequence<1, 1>,                        // Y0、Y1 → major 1 …
                                 sequence<0, 2>>{});                    //      … minor 0、2（第 0、2 段）

  // §3.3 tile window
  const index_t origin = static_cast<index_t>(blockIdx.x) * kTile;
  auto wx = make_tile_window(vx, make_tuple(number<kTile>{}), {origin}, dist);
  auto wy = make_tile_window(vy, make_tuple(number<kTile>{}), {origin}, dist);

  // §3.4 load → 逐元素计算 → store
  auto tx = load_tile(wx);                                 // 本线程的 8 个元素进寄存器
  auto ty = make_static_distributed_tensor<float>(dist);   // 同一分布、未初始化的 tile
  sweep_tile(tx, [&](auto idx) { ty(idx) = alpha * tx[idx]; });
  store_tile(wy, ty);
}

void launch_scale(const float* x, float* y, float alpha, int n, hipStream_t stream) {
  const int grid = (n + kTile - 1) / kTile;   // 每个 block 一个窗口，向上取整
  scale_kernel<<<grid, kThreads, 0, stream>>>(x, y, alpha, n);
}

buffer_load_dwordx4  v[0:3], v8, s[8:11], 0 offen
buffer_load_dwordx4  v[4:7], v8, s[8:11], 0 offen offset:1024
buffer_store_dwordx4 v[0:3], v8, s[0:3], 0 offen
buffer_store_dwordx4 v[4:7], v8, s[0:3], 0 offen offset:1024

第二轮的地址只是第一轮加上立即数 offset:1024（= 64 lane × 4 float × 4 字节），连地址计算都在编译期折叠掉了。§1.1 那段手写的 if/else 尾部处理在这里不存在：最后一个窗口越界的部分由 buffer 指令屏蔽。

这个例子的 block 只有 1 个 wavefront，所以 1 个 P 维正确。a2 的 block 有 4 个 wavefront（kWarps = 4），照抄这里的 encoding 会掉进 §3.2 的那个坑。动手前先按 §3.2 的清单在纸上画出 a2 的 1024 个元素怎样分给 4 × 64 个线程，或者在小部件 3.1 里用小参数试一试。另外 a2 有两个输入、一个输出：想一想各需要几个窗口、几次 load，以及本节开头关于 idx 的那条规则在这里怎么用。
